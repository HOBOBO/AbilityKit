# MOBA 战斗开发流程：复杂需求与规模增长复核

日期：2026-11-18。本文延续 [机制扩展架构分析](MobaMechanismExtensionArchitecture.md) 与 [框架扩展边界](MobaFrameworkExtensionBoundaries.md)，检查已有流程能否长期管理复杂业务，不重新定义 HFSM、Pipeline、Trigger 的职责。

本文包含源码查证和设计推演；推演没有作为战斗测试执行。建议是后续设计和验证依据，不是运行时机制批准。本次不改变运行时、schema、生产配置、发布物或 CI。

## 1. 判断：方向成立，规模化保障仍需补齐

现有流程能够表达多种机制组合，也已经约束权威来源、提交、生命周期、正式帧推进、包依赖和恢复职责。它适合作为继续开发的基础，但不能据此宣称任意复杂组合、大规模压力或跨会话恢复已经闭环。

需要补强的是三层不同的问题：

| 层次 | 已有基础 | 仍要证明 |
|---|---|---|
| 表达能力 | 图、条件/动作、查询、策略和领域运行时可以组合 | 某需求涉及的字段确有消费者，机制语义没有缺口 |
| 组合正确性 | 有唯一 System 树、来源/retain、局部事务和恢复入口 | 竞争、重复、失败、结束边界在组合后仍符合合同 |
| 持续交付能力 | 有权威作者源、校验、门禁定义和报告 | 证据对应实际版本，影响域覆盖足够，容量与迁移成本可控 |

增加一种原语只能解决第一层的一部分。后续应按业务暴露的契约缺口扩展，不以增加节点、策略枚举或英雄数量作为成熟度指标。

## 2. 本轮查证出的流程限制

以下区分当前事实、已有设计与未验证建议，避免把“文档写了”当作“生产已经具备”。

| 查证点 | 事实及边界 | 对流程的影响 |
|---|---|---|
| Trigger 中途拒绝 | [SequenceTriggerPlanExecutable](../Unity/Packages/com.abilitykit.triggering/Runtime/Plans/Executables/SequenceTriggerPlanExecutable.cs) 顺序执行并在失败/停止时退出；[ExecutionControl](../Unity/Packages/com.abilitykit.triggering/Runtime/Core/Execution/ExecutionControl.cs) 记录拒绝；[MOBA runner](../Unity/Packages/com.abilitykit.demo.moba.runtime/Runtime/Application/Services/Triggering/Execution/MobaTriggerPlanExecutorRuntime.cs) 汇总返回结果，这些入口没有通用撤销此前动作的事务 | 不能把一个 Trigger Sequence 当作整笔原子事务；领域内部补偿能力需另查 |
| 帧内派生预算 | [SystemOrderGuide](../Unity/Packages/com.abilitykit.demo.moba.runtime/Runtime/Docs/SystemOrderGuide.md) 明确 Projectile/Area 通知与 due delay 的整轮冻结、16384 项预算和失败会话门禁 | 此预算约束该结算入口，不自动覆盖所有同步 Damage/Trigger 递归、查询、对象数及内存；不能代替合法玩法的连锁终止语义 |
| 局部事务 | [护盾设计 §1.3.5 及后续审计](Moba护盾系统商业化设计.md) 区分盾/HP 的补偿、提交后通知及未来共享资源方案 | 这些内容具有批次与实施范围，不能扩写成所有服务之间已经原子提交；也不应另建覆盖全战斗的万能事务层 |
| 状态一致性指标 | [MobaStateHashBuilder](../Unity/Packages/com.abilitykit.demo.moba.runtime/Runtime/Application/Services/StateSync/MobaStateHashBuilder.cs) 的权威计算读取 inGame、带 Transform 的 Actor 身份/Transform 和当前 HP raw 等 | hash 相等不能排除 Counter、RNG、资格集合、未来任务或来源关系不同；恢复验收要比较受影响的未来充分状态 |
| 本地测试门禁 | [清单](../tools/test-gates.json) 已列 MOBA 配置、内容、验收等 gate；[runner](../tools/run_test_gate.ps1) 检查 TRX 存在、测试数量与结果记录，零命中拒绝，并生成时间/步骤摘要 | 已有入口应复用；一次通过仅证明所执行的步骤，不能将局部门禁写成全部验收 |
| CI 落地 | 清单声明 `.github/workflows/abilitykit-test-gates.yml`；本轮当前工作树中 `.github` 目录及该文件均不存在 | 仓库内自动执行缺证据；不据此推断仓库外没有 CI，也不能按声明认定 PR/定时回归已运行 |
| 证据版本 | runner 当前 gate-summary 写入门禁、状态、时间、步骤等，未见源码 revision、dirty diff、作者源/发布物指纹的自动绑定 | dirty 工作树中仅有 commit 或旧报告日期不足以定位执行输入；可先在批次报告手动关联，再评估脚本补强 |
| 规范矛盾 | [工程化补强方案](Moba中大型项目工程化治理补强方案.md) 原 §3.2.3 曾要求缺少 Trace Registry 阻断正式运行；[依赖校验器](../Unity/Packages/com.abilitykit.demo.moba.runtime/Runtime/Application/Services/Validation/MobaRuntimeDependencyHealthValidator.cs) 要求 Execution Context 等业务依赖，没有将 Trace Registry 列为必需 | 本轮修正文档矛盾，保留 Trace Adapter 可选；缺少 Trace 不等于可以缺少执行上下文、诊断或异常策略 |

以上是流程边界审查，不是完整运行时缺陷清单。恢复方案的批准状态仍应逐批核对，不能从较早治理摘要推导最新实现是否合规。

## 3. 用复杂场景检验流程，而非枚举技能类型

下面是设计推演。每项应能由现有契约回答；不能回答的部分进入具体方案，不能在接英雄时临时选定规则。

| 业务场景 | 必须回答的语义问题 | 当前流程能承担什么、还缺什么 |
|---|---|---|
| 命中触发反伤，反伤又触发吸血/护盾/死亡被动 | 什么是一次命中/伤害事件；派生伤害是否继承资格；零伤害和已死亡目标是否触发；连锁怎样终止 | 来源和正式效果入口可复用；Projectile/Area 的冻结轮次不能自动定义同步伤害递归。新增资格/终止规则需独立方案 |
| 两个来源替换同一技能槽或修改同一参数 | 合成/覆盖谁胜出、平局怎样处理；撤销一个来源后如何恢复；死亡清除哪些来源 | 复用既有贡献合同；每个槽位/参数分别查操作和优先级，不假定所有 Modifier 共享一种仲裁 |
| 先伤害、再召唤，召唤因容量失败 | 整个技能失败、伤害保留还是预先拒绝；付款与冷却如何处理；重试是否再次伤害 | Sequence 不提供整笔撤销；明确可部分成功，或在已有领域服务中定义最小复合提交，不能靠重跑 Trigger 修复 |
| 同帧死亡、重施、到达、超时和取消 | 各入口读哪个时点；哪些是终结原因、哪个先生效；迟到请求能否命中复用后的身份 | 复用正式系统顺序、runtime/generation 和生命周期；给出准确边界例，不用泛化“死亡永远优先”改写全部领域 |
| 主人指令宠物攻击，同时宠物被控且原目标消失 | 指令由谁保存；与自保/攻击/跟随怎样仲裁；指令何时失效；恢复后是否继续 | Brain 输出意图、服务管理生命期的分工成立；新命令、记忆和优先级不是配置已有字段就自然支持 |
| 多段/返程弹体与多个碰撞体、区域共享一次资格 | 按 Actor、Collider、阶段还是 Cast 去重；先过滤还是认领；认领失败是否仍阻挡 | 原语可组合，但资格作用域必须明确；不在每个效果里分别追加去重集合 |
| 飞行中热换投射策略或加载新版配置，再恢复旧检查点 | 活动实例用哪版定义；旧状态由谁解释；客户端/服务端/编辑器版本怎样匹配 | 现有指纹和版本拒绝可查证；没有完整合同前，不宣称任意热更新/跨版本恢复，优先提出会话固定版本的最小方案 |
| 大量召唤与区域造成高频查询和全图技能 | 活动对象、候选集、派生分支、历史保留各有什么预算；超限怎么办 | 现有帧结算预算只是局部保障；目标平台与规模档位需实测，不能按机器负载临时少打几个目标 |
| 回滚后重演技能，客户端已播声音/提示且网络重复投递 | 哪些输出是可重建状态、哪些只播一次；输出身份/确认窗口由谁持有 | 模拟恢复、客户端对账和外部可靠提交分别核对；同会话 journal 不替代重连基线，不补发旧玩法事件 |
| 不同扩展包同时注册同名策略，或扩展在另一场战斗修改静态注册表 | 覆盖/拒绝规则、注册顺序、世界隔离和卸载由谁保证 | 当前注册行为逐入口查证；公开扩展不等于安全热卸载或多世界隔离，不能默默改覆盖规则 |

这些场景可继续增长，但评审维度相对稳定：身份、来源、采样、提交、竞争、终结、容量、版本与输出。固定的是维度和调用边界，具体领域规则保留可扩展性。

## 4. 需要补入开发流程的关键内容

### 4.1 每项复杂变化给出“结果语义”，不只给模块图

复用既有机制记录，按受影响范围补以下信息，不为所有数值改动填写全表：

| 信息 | 最小可审阅内容 |
|---|---|
| 不变量 | 例如同一请求最多创建一个 Actor；移除来源 A 不移除 B；同一终结身份不重复结算。说明对象、作用域与有效窗口 |
| 采样与竞争 | 明确输入/提交/创建/命中/实时读取；同帧先后和同优先级平局规则引用现有合同 |
| 提交边界 | 哪个服务能宣布成功；哪些步骤允许部分成功；失败时已提交结果保留、补偿还是会话失败 |
| 重复与重试 | 身份键、generation、顺序号、保留窗口；正常重复、回滚重演和网络重投分别处理 |
| 终结与后续 | 正常、取消、死亡、替换、过期的责任人；延迟到达如何失效；终结后允许存活的子对象 |

“只执行一次”必须有范围：同一输入请求幂等，不代表不同伤害事件只触发一次；重演未来帧也不是简单忽略原请求。不能用一个永久 HashSet 同时解决这几类问题。

错误至少区分：条件未命中、预期拒绝、已提交后的通知失败、非法配置/不支持版本、不可继续的会话故障。这里只是分析分类，不新增统一运行时枚举。沿既有结果与异常策略表达；若现有返回值无法满足调用方，需要专门设计其契约，不能把所有情况折成 false 后重试。

### 4.2 区分正常补偿、帧恢复和表现对账

- 正常执行失败的补偿由提交所有者处理，仅补偿它能证明属于本次操作的变更，避免覆盖其它合法写入。
- 按帧恢复由已有 Provider/Command 在支持范围内执行，恢复充分状态后重演输入，不把历史效果作为第二套撤销引擎。
- 表现对账从权威可见状态和既有输出身份恢复，不能通过重跑 Trigger 补画面。
- 当前正式帧门禁失败后重建会话，不等于已经撤销该帧所有本地表现和外部通知。

领域原子操作优先封装在现有领域服务，内容层负责编排已声明的语义。只有真实需求要求跨域不可分割结果时，才提出最小协调范围，不默认给整次施法或整帧增加通用事务。

### 4.3 从全部组合回归改为按风险覆盖

组合数随类型增长，不能承诺穷举。采用已有测试框架和正式世界夹具，按变化选择：

1. **原语行为合同**：重点验证输入输出、不变量、拒绝和生命周期，不仅检查类型注册成功。
2. **交互边界**：围绕新改动选择多来源、同帧竞争、父子结束、失败补偿等相交边界；两两覆盖只是起点。
3. **已知高风险长链**：保留 Projectile→Area→Motion、Summon→Brain→Cast/Move、多输入模式等生产切片；新风险可增加切片，不增加对应组合运行时类型。
4. **适用模式**：关闭回滚、启用同会话恢复、所需网络/重连与 Unity Player 分别报告；Editor 或纯 C# 通过不自动覆盖其余环境。

对时间边界选择前一帧、恰好边界、后一帧。对恢复比较关键未来状态和后续结果，不能只比较当前 HP 或局部 hash。故障注入优先在具有部分提交风险的真实边界，断言无重复付款/对象、资格未误消费、来源与 retain 最终释放。

可复用的性质验证包括：不冲突来源改变安装顺序时结果应相同（仅在合同声明可交换时）；撤销 A 保留 B；同一检查点两次重演同一输入得到相同未来结果；同一请求重复投递不额外创建。合法依赖顺序、共享 RNG 消费和目标排序不满足可交换前提时，不套用顺序无关断言。

### 4.4 容量是领域合同的一部分

压测不能只给单 Action 平均耗时。按实际产品确定 Actor/弹体/区域/来源/延迟任务规模、峰值派生数、查询候选数、快照与 Command 保留窗口、表现数量，并记录目标硬件、构建方式、帧率与时长。

同时观察 P95/P99、峰值分配、长稳内存、帧末残留、恢复成本和清理后基线。需要区分合法持续对象与泄漏；Flow 结束但等待合法 child 的 runtime 不能一律判泄漏。

领域硬限、内容静态预检、压力准入和诊断采样各有用途。不得因本机变慢随机跳过伤害、裁剪目标、丢弃正式通知或更改 RNG；改变游戏结果的超限策略必须单独确认。首批阈值依据基线测量提出，不从本文虚构全项目数字。

### 4.5 让证据与发布版本对应

沿用现有报告和发布入口，建议在批次证据中关联：源码 revision 与 dirty 差异/补丁、权威作者源及发布物指纹、能力包版本、运行模式、场景/输入/随机种子、实际执行命令与结果文件、未覆盖范围。复现包按需采集，不要求为普通数值修改建立完整录制系统。

区分包 API 版本、作者 schema 版本、运行时定义指纹、快照/协议版本和资源 revision；其中一个相同不证明其他兼容。旧内容迁移、未知值拒绝、旧检查点处理、升级与回退路径应写在该机制变更中。

活动会话是否固定配置/注册表、是否允许热更新仍依现有合同；若无合同先提案。不能在每次 Tick 隐式读取可变全局注册表实现“热更”。先落实手动证据关联，再决定如何补强 runner/构建流水线，不先建设通用能力数据库或插件平台。

## 5. 需求膨胀时，流程本身也要控制成本

### 5.1 按改动选择工作量

| 改动类型 | 开发与交付最小范围 |
|---|---|
| 已有字段的数值/资源/引用修改 | 查权威源及消费者；做受影响校验、结果/表现和必要发布一致性验证，不重写机制方案 |
| 已定义原语的新组合 | 给简短职责/数据映射，核对来源与提交、竞争、失败和结束，补受影响生产切片；确无新语义则不另行申请机制批准 |
| 新策略、字段或改变语义 | 依治理提交具体方案，补影响域、兼容/恢复、负向和复用证据；包外实现同样适用 |
| 包边界、时序、协议或恢复范围变化 | 明确迁移和旧内容对照，验证独立消费及相关模式；不以单英雄通过替代共享契约验收 |

测试门禁仍以现有清单与规范为准，此处决定应覆盖的风险，不用本文降低已要求的检查。纯文档分析不触发战斗测试，也不把普通字段调整一律升级为全项目重设计。

### 5.2 维护一份当前合同，保留可追溯决策

- 当前规范负责“现在怎么做”，方案负责“为何这样决定、批准哪一范围”，验收负责“哪个版本实际证明了什么”，Skill 只负责选择和执行。
- 新记录明确替代旧记录的哪一条，而非让旧“待确认”和新“已实施”长期并列。历史证据不删除，但不继续当当前状态。
- 受影响的机制记录写明维护责任域、消费者与已知限制。更名/弃用要有迁移对象与退出条件，不无限保留别名或让未知策略落回默认。
- 复用现有引用关系和内容门禁梳理影响：原语/策略→schema/作者源→发布物→消费者→场景。共享修改按消费者选择回归；依赖范围不清时先保守扩大并记录，不能假定静态引用已发现所有动态依赖。
- 并行修改同一权威源时，发布前核对输入基线与差异；导入/导出/发布按既定顺序执行。不能用最后生成的文件覆盖他人的作者源变更来消除漂移。

约束的目标是让新增普通内容主要改变内容/扩展及相关验收。若每接一类技能都必须改核心 DTO、统一枚举、默认装配和多份规范，应回看职责和扩展接点；迁移中的必要核心变更可有明确批次和退出条件，不追求机械的“永远零核心修改”。

## 6. 建议优先级与下一批完成条件

| 顺序 | 建议工作 | 完成条件 |
|---|---|---|
| 先补合同与证据 | 把竞争/部分成功/终结问题附到当前代表切片；修正文档矛盾；确认 CI 声明的实际承载；人工关联版本证据 | 每个所需行为能指出合同和消费者；报告区分实际执行/历史/未验证。CI 缺口单列，不伪报已自动运行 |
| 再验证一个高风险组合和一个包外接点 | 根据真实待开发需求选择，不同时实现全部候选机制 | 正常、拒绝、重复、同帧/跨帧边界、清理和适用恢复有正式结果；基础包无身份分支，外部程序集真实消费 |
| 然后量化规模和收敛发布 | 在目标环境测代表规模和长稳，补证据绑定及迁移检查中最有价值的自动化 | 基线、预算与越界行为有依据；作者源/发布物/测试对应同一输入范围 |
| 持续按需扩充 | 新需求暴露新语义时才扩领域策略、原语或接点 | 每次增长都有明确归属与覆盖，旧内容回归可控，不靠新增万能选项掩盖边界 |

上述排序不是实现授权清单。可以立即继续规范内内容、只读盘点和文档整理；改变竞争规则、事务、输出身份、会话版本或注册语义时，仍按 [机制治理](MobaMechanismGovernance.md) 提交精确方案。无需等待未来所有类型都齐备，按已证明的机制族继续开发。
