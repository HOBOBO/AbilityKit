# 战斗分析平台设计草案

> 状态：供评审的产品与技术方案，尚未进入实现。本文与配套 SVG 都是设计资料；所有编码工作须等用户对整体方案全部确认后再开始。

## 1. 目标与边界

将技能 Trace、离线诊断 Artifact 和真实战斗回放纳入一个可关联、可比较、可视化的战斗分析工作台。分析人员可以从一次战斗会话进入，沿统一帧轴查看输入、执行因果、事件、实体状态和回放画面，并在两次运行或两个版本之间比较差异。

平台负责导入、索引、关联、展示、筛选、导航和导出分析结论。Trace 继续描述执行因果；Artifact 继续承载诊断时刻的快照和相关事实；回放继续拥有驱动战斗执行的输入及其运行时语义。它们不是互相替代的数据格式。

本方案不预设新增运行时机制，不承诺任意时刻可恢复逻辑世界，不改变当前 Replay、Trace、Artifact 的契约，也不确定最终采用 Unity Editor、独立桌面/Web 或双形态。上述选择均列入评审决策。

## 2. 现状与关键约束

- `BattleDebugWindow` 已能打开诊断 Artifact、导出实时诊断快照、加载录像，并从诊断事件/Trace 导航到回放帧，可作为工作台入口的现有基础。
- `BattleDiagnostics` Artifact 保存诊断时收集到的实体/Actor、属性、Buff、Tag、Effect、运行时对象、定义、事件、Trace、帧指标等信息。它是诊断快照/交换文档，不是每帧完整状态历史，也不包含可当然重演的全部输入。
- 回放按帧输入驱动战斗。`BattleReplaySessionOwner` 的 seek 检查点是运行时内存中的检查点；默认回放运行时没有声明可恢复检查点能力。录像索引、渲染快照或传输快照不能自动视为可恢复逻辑世界状态。
- 因此，分析器应明确区分“跳到录像帧”“从输入重演到目标帧”“载入诊断快照”和“从逻辑状态检查点恢复”。界面不得将它们统称为无条件可用的 seek。
- 共享执行链中的任何新行为或新状态恢复语义，均需先按 `Docs/MobaMechanismGovernance.md` 提交方案并获得明确确认；不能通过英雄/技能身份特例实现。

## 3. 用户与主要工作流

### 3.1 定位一次技能异常

1. 打开工作台，载入 Artifact、回放文件或实时诊断导出。
2. 系统展示来源、构建版本、战斗标识、帧范围、采集能力和缺失数据提示。
3. 在事件/Trace 列表按实体、技能、事件类型、严重级别或帧范围筛选。
4. 选择 Trace 节点后，统一时间游标定位到关联帧；回放视图跳帧或按输入重演（取决于来源能力）。
5. 检查参与实体、状态变化、效果/Buff/Tag 变化和上下游因果，形成可分享的书签/分析结论。

### 3.2 复现并逐帧检查

打开真实回放后选择目标帧。若该会话仅支持输入驱动，则从可用起点重演到该帧；若存在经确认的逻辑状态检查点能力，则可从检查点恢复。界面必须展示实际采用的路径、重演范围、输入缺口和恢复能力，且不得静默降级为伪恢复。

### 3.3 比较两次运行或版本

载入两个分析会话并建立对齐关系。默认按战斗帧和实体标识对齐；若帧速率、初始状态、配置或构建不一致，标记为非严格可比。比较事件序列、Trace 结构、指定实体状态、关键指标与回放画面。所有指标展示其来源与比较规则。

### 3.4 从分析结果创建场景

可将选定帧范围、输入、初始化信息及必要资源引用导出为 BattleScenario 候选包。导出前展示缺失引用、非确定性来源和体积估算。Scenario 是分析工件，不隐含服务端上传、发布或自动纳入正式用例。

## 4. 概念模型与数据关联

平台内部建立统一的 `AnalysisSession` 概念，不要求各源数据改成同一文件格式：

| 概念 | 用途 | 典型来源 |
| --- | --- | --- |
| Session | 一次可分析的战斗及其来源、版本、能力声明 | Artifact、录像、实时导出 |
| FrameRef | 帧号、时间与可用帧范围的统一导航键 | 回放索引、事件、Trace |
| EntityRef | 会话内实体标识及可选的跨会话映射 | Actor/实体快照、Trace 参数 |
| EventRef | 事件类型、帧、实体关联及来源位置 | Artifact 事件、运行时事件 |
| TraceRef | 因果节点、父子关系、耗时/结果与源位置 | 技能执行 Trace |
| StateSample | 某一帧/采样点观测到的状态及字段来源 | Artifact 快照、可选逐帧采集 |
| ReplaySource | 输入流、索引、录像资源与驱动能力 | 真实回放文件/会话 |
| BuildManifest | 代码、配置、资源、协议、采集器版本 | 导出元数据 |

关联优先使用稳定的会话内帧号、实体标识和源记录 ID。无法确认的关联应显示“推测/未匹配”，不能伪造确定关系。跨会话实体映射由用户确认或基于明确稳定 ID 规则生成，并保留映射依据。

建议封装层分为：来源适配器（Artifact/Trace/Replay）、规范化索引（session/frame/entity/event/trace）、关联与比较服务、工作台视图。大体量输入和逐帧状态可保留在原始回放/旁路数据中，Artifact 只保存诊断快照与引用，不复制整段数据。窗口与承载边界见[工作区与承载形态规划](BattleAnalysisWorkspaceAndHostingPlan.md)，其中进一步拆分共享基础与 Evidence Explorer、Replay Lab、Runtime Monitor/Control、Comparison 等专用窗口。

## 5. 能力声明与数据完整性

每个数据源应明确声明能力，例如：可浏览帧索引、包含原始输入、可输入重演、支持逻辑状态恢复、包含完整 Trace、包含状态快照、包含逐帧状态历史、包含画面录制。能力需以事实为准，缺失即显示未知/不支持。

建议清晰区分三种状态观察：

1. **诊断快照**：采集时刻的实体/运行时信息，适合排查结构和配置，不代表中间帧历史。
2. **逐帧采样**：按配置采集的状态历史，适合曲线和差异分析；未采样字段不能推断。
3. **逻辑恢复检查点**：可用于恢复并继续模拟的经验证逻辑状态，需由运行时能力明确声明，具有版本和兼容约束。

所有视图应呈现采集覆盖率、丢失/截断情况、采样频率、源构建与配置指纹、schema 版本及时间基准。数据不足时给出局部结论，不把空白当作“没有变化”。

## 6. 工作台信息架构

主工作台由会话/来源栏、中心分析画布、统一时间轴和上下文详情组成。中心画布可切换回放、因果 Trace、事件泳道、状态曲线和比较视图。时间轴游标是跨面板导航状态；筛选和选中实体在切换视图时尽量保留。

主要窗口：

- **会话库/导入器**：来源列表、元数据、校验、兼容性与能力徽标。
- **战斗总览**：回放画面、帧轴、输入/事件/Trace 泳道、实体详情。
- **技能因果图**：技能调用链、子步骤、事件关联、结果与耗时；点击节点联动帧游标。
- **实体状态检查器**：Actor/属性/Buff/Tag/Effect/运行时对象快照；按帧呈现时明确快照或采样来源。
- **状态时间线与差异**：选择实体和字段查看数值曲线、离散变化与字段级 diff。
- **双会话比较器**：帧/事件/Trace/状态/指标并排或叠加比较，显示对齐质量。
- **场景导出器**：选择帧范围、输入与依赖，查看完整性和导出预览。

## 7. 交互与可视分析规范

- 全局时间游标显示绝对帧和相对时间；键盘逐帧前进/后退，播放控制不隐式改变采集源。
- 任一事件、Trace 节点、状态变化和回放帧使用一致的来源标记和选中态。
- 详情面板提供“字段值、来源、观测帧、与前一观测差异、关联事件/Trace”信息。
- 颜色同时搭配图标/文字，避免只靠颜色表达成功/失败或数据缺失。
- 比较视图明确区分相同、不同、未采集、无法对齐；提供原始值与归一化值切换。
- 长时间轴支持缩放、范围选择、事件密度概览和书签；大数据集按窗口加载，不阻塞主线程（具体实现待确认）。

## 8. 非功能要求与兼容性提案

- Artifact 和回放读取应校验 schema/版本并提供可理解的错误；未知字段允许安全忽略或保留，不静默损坏。
- 分析索引可以重建；源文件保持只读。书签、筛选和人工映射作为独立分析元数据保存。
- 统一导出 manifest 记录工具版本、数据源哈希、构建/配置指纹、帧率、时钟基准和能力声明。
- 原始输入、逐帧状态及画面可能远大于 Artifact；建议分块、按需加载，并为逐帧状态采集提供字段白名单/采样率/范围配置。采集策略需要评审确认。
- 离线分析不依赖生产服务；若后续支持团队共享，需单独设计脱敏、访问控制与存储策略，本阶段不展开。

## 9. 分阶段路线（提案）

1. **统一只读入口**：Artifact/Trace/Replay 导入，构建会话索引，元数据和能力提示，统一帧导航。
2. **因果与状态分析**：Trace 节点联动回放，实体检查器，已有数据范围内的事件/快照比较。
3. **状态历史采集评估**：基于用户选定字段和采样策略评估逐帧数据体量、完整性与性能；逻辑恢复能力另行设计和审批。
4. **双会话比较**：对齐策略、事件/Trace/字段状态差异和结果报告。
5. **场景工件闭环**：从回放范围导出 Scenario，验证可重演性与依赖完整性。

各阶段是规划建议，不代表用户已批准新增运行时机制、数据协议或具体 UI 技术栈。

## 12. 时间轴拖动、逻辑复现与表现复现

### 12.1 可行性结论

可以做到“拖动时间轴后在游戏画面看到目标帧，并查看当前实体和战斗数据”，但“任意时刻复现”必须拆成不同能力等级：

- **帧级逻辑复现**：在隔离的 Replay 逻辑世界中，把输入按帧重新驱动到目标帧；画面投影和实体检查器都读取这个逻辑世界。它可以给出真实的当前实体状态，但前提是输入、初始状态、构建、配置、随机源和外部依赖满足确定性条件。
- **逻辑检查点复现**：从经过验证的逻辑检查点恢复，再重演检查点之后的输入。这仍是真实逻辑世界，主要收益是把拖动成本从“从起点重演”降为“从最近检查点重演”。检查点必须覆盖完整可影响结果的状态，并带有兼容性和状态哈希验证。
- **表现快照复现**：读取预采集的实体变换、动画、特效和选定状态字段，快速显示时间轴附近的画面。它适合拖动预览，但不能执行技能、查询未采集的逻辑状态、产生新事件，也不能证明目标帧的逻辑世界可恢复。

因此，产品上应采用“表现预览 + 逻辑确认”的混合模式：拖动过程中先使用可用的表现快照或采样数据反馈；用户松开滑块、点击事件或请求精确检查时，再对隔离逻辑世界执行精确 seek，并将画面投影切换到该逻辑世界。界面要显示当前处于“表现预览”还是“逻辑已确认”，不能让两者看起来等价。

“任意时刻”在逻辑层应定义为离散模拟帧。若时间游标落在两个帧之间，可以对表现做插值，但实体属性、Buff、Tag、Effect、技能状态等逻辑数据仍应指向明确的前一帧或后一帧；插值结果不能被当作实际逻辑状态。

### 12.2 当前代码基础与缺口

- `BattleReplaySessionOwner` 已维护独立的 Replay 会话，`SeekToFrame` 会把输入重演到目标帧；目标帧之前若没有可用检查点，会重建隔离会话后重新推进。这满足“真实逻辑复现”的算法骨架，但长录像或频繁拖动的成本可能较高。
- `DefaultBattleReplaySessionRuntime` 通过 `FrameReplayDriver` 注入每帧输入并调用逻辑会话 Tick，因而目标实体状态可以从 Replay 世界读取，而不是从 Artifact 猜测。
- `BattleSessionFeature` 已有 `ShowReplayView` 和 `BattleWorldProjectionViewSource`，可以把 Replay 世界投影到游戏视图；当前仍受投影资源、活动战斗视图、放置偏移和实体投影能力约束，不能理解成任意多个世界都能无条件渲染。
- 当前默认生产 Replay runtime 没有声明 `IBattleReplayCheckpointRuntime` 能力。`FrameRecordChunkIndex` 只是 seek 锚点，不是可恢复逻辑世界。因此向后拖动的默认正确路径是重建并重演，而不是从录像索引直接恢复。
- Artifact 中的实体、属性、Buff、Tag、Effect 和 Trace 适合解释采集时刻；除非另有逐帧状态历史，否则不能支撑任意历史帧的逻辑状态检查。

### 12.3 三种模式的用户可见行为

| 模式 | 拖动反馈 | 状态检查器 | 能否继续运行/产生新事件 | 结论可信度 |
| --- | --- | --- | --- | --- |
| 表现预览 | 快，按快照/采样显示 | 仅显示已采集字段并标注来源 | 否 | 画面近似或采样事实 |
| 输入重演 | 可能等待重演，按帧更新 | 读取 Replay 逻辑世界 | 可以继续播放；修改输入应视为新分支 | 满足确定性时为逻辑事实 |
| 检查点恢复 + 重演 | 等待最近检查点后的短段重演 | 读取恢复后的逻辑世界 | 可以继续播放；检查点后可产生新分支 | 满足检查点契约时为逻辑事实 |

在拖动请求尚未完成时，界面应显示目标帧、实际已确认帧、重演进度、使用的模式和失败原因。取消或再次拖动应使旧请求失效，避免旧的重演结果覆盖新的游标。

### 12.4 要做到“完全逻辑可复现”必须具备的条件

1. 固定并记录世界初始状态、模拟帧率、构建版本、配置/资源指纹、协议 schema 和随机种子/随机流位置。
2. 将实体 ID 分配器、生命周期、技能/HFSM、Buff/Tag/Effect、投射物、计时器、延迟队列、物理/寻路结果、脚本协程、对象池和所有影响结果的缓存纳入确定性状态边界。
3. 对网络、时间、文件、线程调度、平台差异等外部输入做录制、隔离或确定性替代；未捕获的外部副作用必须使能力声明降级。
4. 在关键帧或每帧计算状态哈希，并在重演后与原始记录/检查点比对；哈希不一致时显示“不可证明”，不能继续宣称精确复现。
5. 检查点必须由完整的恢复提供者注册表生成，带世界身份、构建/配置兼容范围、状态哈希和版本迁移策略；只保存 Actor 变换或渲染对象不足以恢复逻辑世界。
6. 逻辑 Replay 世界与生产战斗世界、输入通道、共享上下文和表现资源保持隔离；投影只订阅 Replay 世界，不能把拖动操作写回实时战斗。

### 12.5 推荐的产品落地顺序

1. **首期**：统一时间轴、事件/Trace 联动和真实 Replay 投影；滑块松开后执行帧级输入重演，状态检查器读取逻辑 Replay 世界，并明确显示等待和重演路径。
2. **性能增强**：为已确认的完整状态提供逻辑检查点和哈希索引；拖动时采用最近检查点 + 输入重演，仍保留从起点重演的正确性回退。
3. **快速预览**：对选定实体和表现字段增加可选采样/快照流，用于拖动期间的低延迟预览；预览数据和逻辑确认结果分层展示。
4. **高级分析**：支持帧级状态差异、分支输入、确定性验证报告和 Scenario 导出；任何新恢复语义仍需单独经过机制治理确认。

这个顺序能实现可用的“拖动查看 + 真实状态排查”，同时避免把无法恢复的渲染快照、录像索引或诊断 Artifact 误当作完整逻辑世界。

### 12.6 需要用户确认的新增决策

- 时间轴的精确目标是“帧边界逻辑状态”，还是还要承诺帧间的连续表现插值。
- 拖动时是否接受“松开后精确重演”的交互，还是要求每个鼠标移动位置都得到逻辑确认；后者需要检查点或逐帧状态缓存支撑。
- 第一阶段是否允许表现预览与逻辑确认短暂不同步，并在界面上明确标注两者。
- 是否把“可继续运行并产生新分支”纳入回放工具；若纳入，需要定义分支输入格式、父会话指纹和比较规则。

## 13. 帧同步回滚与离线分析的定位边界

### 13.1 结论

把帧同步回滚、隔离 Replay、Trace 和 Artifact 放进同一个产品入口是合理的；把它们当成同一种“回放状态”或由同一个执行引擎处理则不合理。

更准确的产品定位是 **Battle Analysis Workbench**：它统一会话、时间轴、实体引用、构建元数据和视图导航，但下面挂载不同能力域：

1. **Runtime Control / 运行时控制**：面向正在运行或可恢复的游戏逻辑世界，执行回滚、重演、继续运行和输入分支。
2. **Replay Lab / 隔离重演**：在不影响生产战斗的独立逻辑世界中按帧重演输入，验证目标帧的逻辑状态。
3. **Evidence Analysis / 离线证据分析**：读取 Trace、Artifact、逐帧采样和画面记录，解释已经产生的事实，不主动驱动游戏世界。

统一的是分析工作流和关联键，不是状态来源、生命周期、可写权限或恢复语义。

### 13.2 为什么帧同步回滚不是普通离线分析

帧同步回滚通常发生在真实游戏运行时或与其同构的实时运行时中。它的目标是恢复到某个已知逻辑节点，再用输入重新推进，以便修正预测、追赶权威状态或继续当前战斗。它具有以下特征：

- 状态可能属于当前游戏会话，回滚完成后通常还要继续推进到“现在”；
- 输入、网络确认、时钟和外部服务可能继续变化；
- 回滚可能影响当前可见实体、输入接收和表现生命周期；
- 可回滚范围受保留窗口、权威快照和状态存储限制，并不等于任意历史时刻；
- 回滚后的世界仍然是可执行的，可能继续产生事件、副作用或新的输入分支。

因此，“拖动时间轴”如果直接操作实时战斗，实际上是在发出运行时控制命令，不是简单地移动一个离线观察游标。它必须有暂停/恢复、权限、并发、超出回滚窗口、网络追赶和副作用处理等明确契约。

### 13.3 离线分析的时间轴语义

离线分析时间轴默认是只读观察游标。它可以：

- 定位 Artifact 的快照帧和 Trace 节点；
- 在已有逐帧数据上查看字段变化；
- 请求隔离 Replay 世界执行输入重演；
- 将结果投影到专用分析画面。

它不应默认：

- 修改线上或当前生产战斗世界；
- 把一个静态快照恢复成可运行逻辑世界；
- 把录像索引、渲染快照或网络传输快照当作完整检查点；
- 让用户在未声明能力的情况下继续执行并产生新的正式战斗结果。

### 13.4 推荐的统一方式：一个工作台，三种时间操作

同一个界面可以显示统一时间轴，但时间轴上的操作应按能力显式分流：

| 操作 | 目标对象 | 实际含义 | 是否改变运行时 |
| --- | --- | --- | --- |
| 观察游标移动 | Artifact / Trace / 采样历史 | 定位已记录事实 | 否 |
| 隔离 Replay seek | 独立 Replay 世界 | 重建或检查点恢复后按输入推进 | 只改变隔离世界 |
| Runtime rollback | 真实或专用实时运行时 | 恢复运行时状态并重新推进 | 是，需权限和契约 |
| 表现快照预览 | 采样画面/实体表现 | 显示近似或采集到的表现 | 否 |

四者可以共享帧号、实体 ID、Trace 关联和构建指纹，但 UI 必须显示当前操作类型、目标世界、可写性、恢复来源和确认状态。

### 13.5 实时回滚与离线分析的关联点

两者最适合在“证据关联”处结合，而不是在“状态存储”处强行合并：

- 实时回滚产生的诊断事件、输入窗口、状态哈希和回滚前后差异可以导出为 Artifact；
- 线上异常的 Trace/Artifact 可以提供 Runtime Control 或 Replay Lab 的定位帧和筛选条件；
- Runtime Control 的回滚验证结果可以与离线 Replay 的重演结果进行双会话比较；
- 若两者构建、配置、初始状态和随机流不兼容，平台应标记为“关联但不可直接证明等价”。

不建议让 Artifact 直接承载可继续运行的完整逻辑状态，也不建议让离线分析器通过共享全局上下文去控制真实战斗。两类系统应通过明确的导出/导入协议和会话指纹连接。

### 13.6 对现有原型和术语的调整建议

- 将“时间轴拖动”拆成“观察游标”“隔离重演”“运行时回滚”三个按钮或模式，而不是一个无歧义的 Seek。
- 将“逻辑已确认”限定为目标 Replay/Runtime 世界已经完成指定帧的逻辑推进并通过校验；Artifact 快照只显示“已观测”。
- 在工作台顶部显示 `World: Live Runtime / Isolated Replay / Offline Evidence`，并显示 `Read-only / Executable / Branchable` 能力标签。
- Runtime Control 使用独立的危险操作区和确认状态；离线分析的筛选、书签和比较操作不应触发运行时副作用。
- 仍可保留统一的实体详情、Trace、状态差异和构建元数据面板，但详情中必须标注每一字段来自哪个世界和哪种证据。

按这个边界，平台既能让开发者从离线证据跳到真实运行时排查，也能让同一时间轴比较回滚前后、隔离重演和 Artifact 记录；同时不会因为共用一个 UI 就误把三种不同的时间和状态语义混成一种能力。
