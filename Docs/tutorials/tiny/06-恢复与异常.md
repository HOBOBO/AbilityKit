# 06 恢复与异常

**目标：** 把断线、帧队列溢出、快照失配与历史耗尽统一落到可验证的全量恢复路径。

## 章节契约

- 前置：先跑通选定模式：[03 状态同步](03-状态同步.md)或[04 帧同步与回滚](04-帧同步与回滚.md)/[05 混合同步](05-混合同步.md)；不增加新的战斗规则包。
- 框架提供：连接恢复状态、Room 恢复流程、有界帧收件箱与全量快照游标。
- 项目实现：恢复请求时机、当前战斗的 World 绑定、暂停输入、正确应用快照后恢复帧流，以及界面状态。
- 教学代码：可导入片段展示历史耗尽；独立验收工程分别触发断线、帧溢出和周期快照失配，复用正式会话、Room 收件箱与复制器。

## 验收与边界

Frame/Hybrid 路径可导入 `06 Recovery` 并运行 `TinyRecoveryExample.Run()`；它将历史容量设为 2，推进 3 帧后验证 `NeedsFullSnapshot`，应用权威全量状态后继续预测并比较哈希。仓库内可先运行 `dotnet run --project src/AbilityKit.Demo.Tiny.ChapterSamples`。单独复查离线故障时，运行 `dotnet run --project src/AbilityKit.Demo.Tiny.RecoverySample -- history`，或将末尾参数换成 `overflow`、`mismatch`。

联机验收运行 `./tools/verify-tiny-starter.ps1 -SkipUnity`。`recovery-sample.log` 应分别包含四行 `06 ... passed`：

| 故障 | 注入与恢复判据 |
| --- | --- |
| `history-exhaustion` | 丢失容量为 2 的预测历史，要求全量状态，恢复后继续预测且哈希一致。 |
| `overflow` | 容量为 2 的 Room 收件箱接收第 3 帧时溢出，最低恢复帧为 13；World 错误、旧帧、非全量快照均不推进游标；覆盖缺口的快照后恢复帧流。 |
| `snapshot-mismatch` | 本地预测与服务端周期快照哈希不同，复制器校正一次，权威哈希一致，之后可继续预测。 |
| `disconnect` | 双客户端 Frame 会话断开访客连接，以原账号重连并恢复同一战斗的完整基线。 |

三模式综合日志中的 `session-state.log`、`session-frame.log`、`session-hybrid.log` 也应包含 `reconnect=full`。断线入口是 `RecoverConnectionAsync`；帧溢出入口是 `TryGetFrameOverflow`，随后通过 `RequestFullSnapshotAsync` 取得覆盖缺口的快照。两者位于 `Runtime/View/TinyBattleSession.cs`；有界收件箱与游标由 Room 包提供。

恢复期间不提交新帧输入；旧快照不能覆盖丢失帧缺口；无效快照不能推进已确认游标。无头验收覆盖逻辑与 TCP 行为；隔离 Unity 网络 PlayMode 还验证同进程两套正式会话在 State、Frame、Hybrid 下重建访客连接、重新绑定原战斗并投影完整基线。双可视化 Unity 客户端的画面交互仍属于独立场景验收。

## 首个基线等待

订阅成功和全量快照请求被接受都不等于客户端已有可用基线。State 要等当前 World 的完整角色快照；Frame/Hybrid 要等当前 World 的完整 Tiny 状态载荷成功应用。等待期间三种模式都暂停输入，界面显示 `Waiting for baseline`。请求被拒绝或推送未到时，场景侧每隔两秒重试；连接恢复与快照请求不会并行。错误 World、非全量或不可用快照不会解除等待。

`TinyBattleSessionTests` 用延迟与缺失快照验证上述状态转换；双客户端 TCP 验收仍负责验证正常链路上的真实推送。若要复查无推送故障，运行隔离 Unity 工程的无头 EditMode 测试，不需要操作桌面 Unity。

所有 Room 请求使用启动请求中的期限；快照请求、帧订阅和战斗输入也有本地期限。Hybrid 输入超时后要求全量快照恢复，避免继续基于未确认的预测提交输入。连接失效时，场景取消正在等待的命令、轮询或快照请求，再执行 Room 恢复。恢复期间不自动重发建房；命令超时后的服务端结果仍需由权威房间状态确认。若恢复为空房间，正式会话保留待确认的建房命令 ID 和同步模式，用户重试时复用它们；已关闭房间不会因旧命令重放而重新绑定账号。
