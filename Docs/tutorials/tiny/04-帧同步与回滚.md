# 04 帧同步与回滚

**目标：** 使用框架的历史、快照和回滚协调器处理权威输入帧，并能解释一次迟到输入为何触发重放。

## 章节契约

- 前置：[01 规则与确定性](01-规则与确定性.md)和[02 房间与连接](02-房间与连接.md)；新增 `com.abilitykit.world.framesync`。
- 框架提供：`InputHistoryRingBuffer`、`RollbackSnapshotRingBuffer`、`WorldStateHashRingBuffer` 与 `RollbackCoordinator`。
- 项目实现：Tiny 规则状态的捕获/恢复、输入映射、权威哈希核对和历史缺失时的停止条件。
- 教学代码：只展示创建回滚会话、预测一帧和应用迟到权威帧；完整适配见 `Runtime/FrameSync/TinyFrameSyncSession.cs` 与 `Runtime/View/Sync/TinyFrameReplication.cs`。

## 验收与边界

导入 `04 Frame` 样例并运行 `TinyFrameExample.Run()`；它先预测空帧，再应用迟到的权威攻击，要求返回 `Replayed` 且哈希一致。已有 Host/Gateway 时可运行 `dotnet run --project src/AbilityKit.Demo.Tiny.FrameSample -- 127.0.0.1 4058 my-run`。该工程先共编译并执行 UPM 本地样例，再经正式 `TinyBattleSession` 验证两端 Frame 权威结果收敛；日志给出本地 `chapterHash`、权威帧号及双方回滚计数。服务端周期快照可能先于迟到帧覆盖结果，因此网络计数允许为零；回滚行为由本地样例和复制器定向测试断言。统一门禁 `./tools/verify-tiny-starter.ps1 -SkipUnity` 将结果写入 `frame-sample.log`，并保留 `frame.log` 的网络哈希收敛、`session-frame.log` 的恢复验收。`AbilityKit.Demo.Tiny.Replication.Tests` 验证同一份 `TinyFrameReplication` 源码。正式回滚适配在 `Runtime/FrameSync/TinyFrameSyncSession.cs`，会话输入入口在 `Runtime/View/TinyBattleSession.cs`。

权威输入到来后双方在同一帧的哈希一致；历史不足或哈希无法收敛时要求全量快照，不继续输出伪造的结果。隔离工程的无头 PlayMode 测试还驱动正式会话和角色 View：权威输入帧更新现有角色对象，哈希失配期间保持最后一次有效投影，全量快照恢复后继续更新同一对象。这是 Unity 对象状态的证据，最终画面仍需可视化客户端验收。本章不引入本地主控即时预测的产品语义，它由 05 说明。

正式会话使用提交响应中的服务端帧号安排后续输入。Frame 模式遇到“帧已处理”时，会把同一输入最多重排提交三次；连续过期后明确报错，避免无限重试。“帧过早”要求重新取得全量基线；限速只丢弃本次输入并保留当前基线。输入模块在请求未完成时仍采样按键，保留最新移动方向和至多一次待发送攻击，连接或基线不可用时清空待发送动作。
