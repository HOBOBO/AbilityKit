# 07 正式项目装配

**目标：** 将前几章能力组装为可移动、可测试、职责清晰的 Unity 与服务端项目。

## 章节契约

- 前置：完成 01–03 的 State 主线，或完成 01、02、04 的 Frame 分支；选择 Hybrid 时再完成 05。按选定模式学习 06 恢复。完整 Unity 包声明 Logic、DemoCommon、View Runtime、Room、Network、Protocol 和 World.FrameSync 依赖；后者通过包依赖闭包提供 MemoryPack 所需的 Unsafe 程序集。Starter 只是可选入口，按需导入 Samples 不会减少包依赖。
- 客户端：独立 Logic 包只管规则；`Runtime/FrameSync` 只管回滚适配；`Runtime/View` 管会话、输入与表现；`Composition` 管 Profile/Prefab；`Scenes` 管可运行场景。外部项目将 Tiny 场景及自己的大厅场景加入 Build Settings，认证后调用 `TinyProjectLaunch.Open(launch, returnScene)` 进入 Tiny。该入口同时发布共享 Bootstrap 所需的玩法和多人启动请求。
- 服务端：`Server/Orleans/src/AbilityKit.Demo.Tiny.Server` 提供 Room/Battle 适配、同步模板与模块声明；Host 的组合根注册 `TinyServerGameplayModule.Create()`，Grains 通过注入的 `ServerGameplayModuleCatalog` 解析玩法。
- 教学代码：展示项目装配点和可替换策略，不重新实现 Room、SDK、Loading 或 View 模块宿主。

## 交付门槛

用 `./tools/create-tiny-validation-project.ps1 -Standalone` 生成不含 Starter 的消费工程。它嵌入 Tiny 依赖闭包，包含 `ConsumerLobby`、项目侧 `TinyConsumerLobby.Enter(authenticatedLaunch)` 和一条无头 PlayMode 进场测试；调用方仍负责认证并提供有效会话令牌。普通模式保留 Starter 验收工程。`./tools/verify-tiny-starter.ps1` 完成依赖层级、协议、.NET、三模式 TCP，以及两种工程的 Unity 批处理验收。可传入 `-SiloPort`、`-OrleansGatewayPort`、`-TcpPort`、`-HttpPort` 避开已占用端口。TCP 阶段每种模式还分别运行房主和访客两个独立 .NET 进程，保存 PID、房间、战斗、权威攻击和重连证据。隔离 Unity 网络 PlayMode 使用真实 Gateway 驱动两个正式会话及角色 View，检查三种模式和访客重连；普通 PlayMode 验证项目入口、场景、Bootstrap 和对象生命周期。这些无头证据不验证最终画面。

消费工程另有 `TinyConsumer.Network.PlayMode.Tests`：从自有大厅调用 `TinyProjectLaunch.Open`，由场景中的 `TinyGameplayRoot` 连接真实 Gateway；第二个正式会话作为网络对端。它逐模式验证建房、加入、准备、Loading、开战、攻击投影、访客重连和返回大厅，结果写入 `tiny-consumer-network.json`。这是一个 Unity 进程加一个同进程网络对端的无头验收，不代表两台可视化 Unity 客户端的画面验收。

如果项目选择回合制，运行 `./tools/create-tiny-validation-project.ps1 -Standalone -IncludeTurn`。额外的 `ConsumerTurnLobby` 通过项目侧 `TinyConsumerTurnLobby.Enter` 调用 `TinyTurnProjectLaunch.Open`，`TinyConsumer.Turn.Network.PlayMode.Tests` 从这个大厅进入可选 Turn 场景，通过真实 Gateway 完成三回合并返回大厅。默认 `-Standalone` 不含 Turn 包和这个入口。验证结果位于 `tiny-consumer-turn-network.json`。

## 同步与节奏选择

完整门禁会为 Hybrid、Frame、State、Turn 分别生成房主与访客两个独立消费工程，同时启动两个无头 Unity 进程。`unity-cross-{Mode}/` 保存两侧 XML、日志和 JSON，验证不同 PID、同一房间/战斗、场景 Root、权威结果与返回大厅；Hybrid 额外验证提交前预测，Frame/Hybrid 的访客重新进入场景后验证完整基线恢复。可用 `./tools/verify-tiny-starter.ps1 -FocusTurnRecord -VerifyCrossProcess` 定向重跑 Turn 与双进程链路。该证据不包含最终画面质量判断。

| 项目约束 | 首选演示 | 先验证什么 | 进入下一章 |
| --- | --- | --- | --- |
| 低频、单行动者、按回合结算 | 10 Turn（State） | 行动所有权、提交后等待权威回合、重连与续号 | 02–03、06、10 |
| 实时玩法，以服务端状态为准 | 03 State | 权威快照、插值与恢复 | 01–03、06 |
| 相同规则可确定性复演，愿意处理迟到输入 | 04 Frame | 帧历史、回滚后哈希一致 | 01–02、04、06 |
| 需要本地即时响应且保留权威校正 | 05 Hybrid | 提交前预测、快照失配后恢复 | 01–02、04–06 |

先按战斗节奏和客户端响应要求选路径，再决定快照频率与输入策略。Turn 是独立玩法包，不要求实时项目迁移到回合制；Record/Replay 属于 09 的可选诊断层，不能代替线上同步模式。

## 三种模式的对照证据

同一攻击在 `tiny-consumer-network.json` 中应满足下表；所有模式都必须有角色投影、访客完整基线恢复和返回大厅。`authoritativeFrame`、`predictedFrame`、预测/回滚/校正/恢复计数来自正式会话的 `TinySyncTelemetry`。

| 模式 | 发送完成前的本地预测 | 权威结果 | 预期用途 |
| --- | --- | --- | --- |
| State | 无 | 两端读取权威快照 | 最容易先完成的联机主线 |
| Frame | 无 | 权威输入帧推进相同规则 | 确定性帧历史与回滚 |
| Hybrid | 有，`predictedBeforeConfirmation=true` | 权威帧确认，周期快照校验 | 本地即时响应与校正 |

网络时序可能让回滚或校正计数保持为零，因此这些计数只作观测，不作为“必须出现回滚”的证明。迟到帧重放由 04/05 的定向样例和复制器测试断言；快照失配由 05/06 的故障注入验收断言。

## 项目侧替换点

| 决策 | Tiny 的默认位置 | 新项目应替换的内容 |
| --- | --- | --- |
| 认证与进场 | 消费工程的 `TinyConsumerLobby.Enter`、`TinyProjectLaunch` | 账号、会话令牌、Gateway 地址、返回场景 |
| 规则和状态格式 | Logic 包的 `TinyBattle`、`TinyInput`、`TinyBattleStateCodec` | 输入语义、确定性状态、编解码与哈希；客户端和服务端共用同一份源码 |
| 服务端玩法 | `TinyServerGameplayModule.Create()` | Room 描述、同步模板、World 和 Battle 适配 |
| 客户端会话策略 | `TinyBattleSession` | 房间标签、输入提交、快照映射、恢复判据 |
| 输入与表现 | `TinyInputModule`、`TinyActorViewModule`、`TinyHudPresenter` | 控制方式、角色对象和状态展示 |
| Loading | `TinyAssetPreparation` | 有真实资源时注册资源准备步骤；Tiny 的程序化场地只验证启动清单 |

先运行完整门禁，再做 08 的规则变更练习。同步 schema 当前限定为版本 1；不兼容版本会在 `TinyBattleSession` 能力协商时拒绝，订阅、基线请求和输入均不应继续。`IncompatibleSchemaStopsBeforeSubscriptionAndInput` 是对应的定向证据。Loading 与战斗订阅还会校验启动清单哈希，防止客户端规则或场地标识与服务端不一致；修改规则时应同步升级共享 Logic 中的 `RulesKey`，此检查不代替同步 schema 协商。

服务端发布包中的 `composition/TinyCustomHost.csproj` 是仓库外可编译的组合入口。项目可在 `ConfigureGameplay` 注册自己的 `ServerGameplayModule`，并让该 Host 与同一发布包的 Gateway 配套运行；`-ServerBundlePath <目录> -UseCompositionHost` 可用真实 TCP 样例验证这条路径。

消费工程的 `Assets` 不包含从源码工程复制的 DLL；Unsafe 程序集随 `com.abilitykit.thirdparty.unsafe` 包分发。验收脚本会检查该包存在，并拒绝 `Assets` 下额外的 DLL。首次导入仍需从 OpenUPM 和 Unity Registry 获取公共包。

当前仓库没有 Tiny 的 CI workflow。开发者可在本地运行 `./tools/verify-tiny-starter.ps1 -SkipUnity` 检查 .NET 与 TCP 阶段，或运行完整命令，在隔离工程中以 `-batchmode -nographics` 执行 Unity 验收。每次运行在 `local/Logs/tiny-acceptance-*/phases.json` 记录实际运行或跳过的阶段；独立进程的 `process-{Mode}/owner.json`、`guest.json`，以及 Unity XML、JSON 和 TCP 日志保存在同一目录。完整门禁还产生 `unity-cross-{Mode}/` 证据，具体覆盖的模式以当次 `phases.json` 和目录为准。

正式项目代码只能存在一份；`Samples~` 里的章节脚本只负责演示公开 API 的装配，不能成为生产会话的隐式依赖。
