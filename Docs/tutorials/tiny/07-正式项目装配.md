# 07 正式项目装配

**目标：** 将前几章能力组装为可移动、可测试、职责清晰的 Unity 与服务端项目。

## 章节契约

- 前置：完成 01–03 的 State 主线，或完成 01、02、04 的 Frame 分支；选择 Hybrid 时再完成 05。按选定模式学习 06 恢复。Unity 版本与直接依赖见 [客户端包声明](../../../Unity/Packages/com.abilitykit.demo.tiny/package.json)，其中直接声明了 MemoryPack 所需的 Unsafe 包。Starter 只是可选入口，按需导入 Samples 不会减少包依赖。
- 客户端：先按[包内接入指南](../../../Unity/Packages/com.abilitykit.demo.tiny/Documentation~/IntegrationGuide.md)完成项目大厅、场景与入口准备。独立 Logic 包只管规则；`Runtime/FrameSync` 管回滚适配；`Runtime/View` 管会话、输入与表现；`Composition` 管装配资源；`Scenes` 管可运行场景。职责划分见 [Tiny 接入基线](../../design/09-ImplementationExamples/TinyStarterImplementation.md)。
- 服务端：`Server/Orleans/src/AbilityKit.Demo.Tiny.Server` 提供 Room/Battle 适配、同步模板与模块声明；Host 的组合根注册 `TinyServerGameplayModule.Create()`，Grains 通过注入的 `ServerGameplayModuleCatalog` 解析玩法。
- 教学代码：展示项目装配点和可替换策略，不重新实现 Room、SDK、Loading 或 View 模块宿主。

## 交付门槛

### 先验证自有大厅（无需服务端）

在仓库根目录运行。按 [`ProjectVersion.txt`](../../../Unity/ProjectSettings/ProjectVersion.txt) 选择 Unity Editor，将 `$unity` 改为本机路径：

```powershell
$unity = 'C:\Program Files\Unity\Hub\Editor\2022.3.62f1\Editor\Unity.exe'
$run = Join-Path (Get-Location).Path ("local/Logs/tiny-consumer-" + (Get-Date -Format 'yyyyMMdd-HHmmss'))
$null = New-Item -ItemType Directory -Path $run -ErrorAction Stop
$project = Join-Path $run 'consumer'
./tools/create-tiny-validation-project.ps1 -Standalone -OutputPath $project
if (-not $?) { throw 'Tiny consumer project generation failed.' }
$results = Join-Path $run 'scene-playmode.xml'
$editorLog = Join-Path $run 'scene-playmode.log'
$argsList = @('-batchmode', '-nographics', '-projectPath', "`"$project`"",
    '-runTests', '-testPlatform', 'PlayMode', '-assemblyNames', 'TinyConsumer.PlayMode.Tests',
    '-testResults', "`"$results`"", '-logFile', "`"$editorLog`"")
$editor = Start-Process -FilePath $unity -ArgumentList $argsList -WindowStyle Hidden -Wait -PassThru
if ($editor.ExitCode -ne 0 -or -not (Test-Path -LiteralPath $results)) { throw "See $editorLog" }
[xml]$report = Get-Content -LiteralPath $results -Raw
if ($report.'test-run'.passed -ne '1' -or $report.'test-run'.failed -ne '0') { throw "See $results" }
```

生成器将本地包嵌入 `consumer/Packages/`，不引用原仓库绝对路径。还需要按 manifest 配置解析公共包，因此这不是离线安装。检查 `ProjectSettings/EditorBuildSettings.asset` 已启用 `Assets/Scenes/ConsumerLobby.unity` 与包内 `TinyDemoGameplayScene.unity`；默认不含 Starter 或 Turn。

[`OwnLobbyLaunchesTinyWithoutStarter`](../../../tools/tiny-consumer-template/Assets/Tests/TinyConsumerPlayModeTests.cs) 从 `ConsumerLobby` 调用 [`TinyConsumerLobby.Enter`](../../../tools/tiny-consumer-template/Assets/Scripts/TinyConsumerLobby.cs)，检查 Bootstrap 生成 `TinyGameplayRoot`、消费启动请求并返回原大厅。它使用测试令牌和不可用的本地端口，不验证登录、连接或战斗。模板不提供真实登录 UI；项目需要把自己的登录流程接到 `Enter`。

| 停在哪一步 | 先看什么 |
| --- | --- |
| 工程生成拒绝 | 输出必须在源 `Unity/` 工程之外，且不存在或为空；换新目录，不覆盖上次证据 |
| Unity 导入失败或没有 XML | 查看 `scene-playmode.log` 的首个包解析、编译或许可错误；核对 Unity 版本、manifest 注册表与依赖，不从源工程复制 DLL 补依赖 |
| XML 没有目标测试或断言失败 | 确认筛选 `TinyConsumer.PlayMode.Tests`；核对两个场景已启用、大厅挂有 `TinyConsumerLobby`，且直接进 Tiny 场景不等同于调用大厅入口 |
| 场景测试通过但联机失败 | 先查 Gateway 地址、有效令牌、Host 玩法注册与两端版本；再按[恢复章](06-恢复与异常.md)排查基线。场景测试不验证任何同步模式 |

### 再验收联机

运行 `./tools/verify-tiny-starter.ps1` 执行协议、.NET、TCP 和 Unity 的完整仓库验证；普通模式仍保留 Starter 验收。可传入 `-SiloPort`、`-OrleansGatewayPort`、`-TcpPort`、`-HttpPort` 避开已占用端口。TCP 阶段为每种实时模式分别运行房主和访客两个 .NET 进程，记录 PID、房间、战斗、权威攻击和重连。若 `phases.json` 显示协议预检失败，不能将后续 TCP 与 Unity 阶段计为通过。

消费工程另有 `TinyConsumer.Network.PlayMode.Tests`：从自有大厅调用 `TinyProjectLaunch.Open`，由场景中的 `TinyGameplayRoot` 连接真实 Gateway；第二个正式会话作为网络对端。它逐模式验证建房、加入、准备、Loading、开战、攻击投影、访客重连和返回大厅，结果写入 `tiny-consumer-network.json`。这是一个 Unity 进程加一个同进程网络对端的无头验收，不代表两台可视化 Unity 客户端的画面验收。

如果项目选择回合制，运行 `./tools/create-tiny-validation-project.ps1 -Standalone -IncludeTurn`。额外的 `ConsumerTurnLobby` 通过项目侧 `TinyConsumerTurnLobby.Enter` 调用 `TinyTurnProjectLaunch.Open`，`TinyConsumer.Turn.Network.PlayMode.Tests` 从这个大厅进入可选 Turn 场景，通过真实 Gateway 完成三回合并返回大厅。默认 `-Standalone` 不含 Turn 包和这个入口。验证结果位于 `tiny-consumer-turn-network.json`。

手工验收最终画面时，用 `./tools/create-tiny-validation-project.ps1 -OutputPath <目录>` 分别生成两个 Starter 工程，再按本地环境启动 `./Server/Orleans/tools/start_orleans_dev.ps1`。两份工程分别打开 `StarterScene` 并指向同一 Gateway；使用不同账号，再按[包内接入指南](../../../Unity/Packages/com.abilitykit.demo.tiny/Documentation~/IntegrationGuide.md)完成建房、开战与返回。不得让两个编辑器共用工程的 `Library`。

## 同步与节奏选择

完整门禁会为 Hybrid、Frame、State、Turn 分别生成房主与访客两个独立消费工程，同时启动两个无头 Unity 进程。`unity-cross-{Mode}/` 保存两侧 XML、日志和 JSON，验证不同 PID、同一房间/战斗、场景 Root、权威结果与返回大厅；Hybrid 额外验证提交前预测，Frame/Hybrid 的访客重新进入场景后验证完整基线恢复。可用 `./tools/verify-tiny-starter.ps1 -FocusTurnRecord -VerifyCrossProcess` 定向重跑 Turn 与双进程链路。该证据不包含最终画面质量判断。

| 项目约束 | 首选演示 | 先验证什么 | 进入下一章 |
| --- | --- | --- | --- |
| 低频、单行动者、按回合结算 | 10 Turn（State） | 行动所有权、提交后等待权威回合、重连与续号 | 02–03、06、10 |
| 实时玩法，以服务端状态为准 | 03 State | 权威快照、插值与恢复 | 01–03、06 |
| 相同规则可确定性复演，愿意处理迟到输入 | 04 Frame | 帧历史、回滚后哈希一致 | 01–02、04、06 |
| 需要本地即时响应且保留权威校正 | 05 Hybrid | 提交前预测、快照失配后恢复 | 01–02、04–06 |

先按战斗节奏和客户端响应要求选路径，再决定快照频率与输入策略。Turn 是独立玩法包，不要求实时项目迁移到回合制；Record/Replay 属于 09 的可选诊断层，不能代替线上同步模式。

## 三种模式的对照证据

同一攻击在 `tiny-consumer-network.json` 中应满足下表；所有模式都必须有角色投影、访客完整基线恢复和返回大厅。`authoritativeFrame`、`predictedFrame`、预测/回滚/校正/恢复计数来自正式会话的 `TinySyncTelemetry`。

| 模式 | 发送完成前的本地预测 | 权威结果 | 预期用途 |
| --- | --- | --- | --- |
| State | 无 | 两端读取权威快照 | 最容易先完成的联机主线 |
| Frame | 无 | 权威输入帧推进相同规则 | 确定性帧历史与回滚 |
| Hybrid | 有，`predictedBeforeConfirmation=true` | 权威帧确认，周期快照校验 | 本地即时响应与校正 |

网络时序可能让回滚或校正计数保持为零，因此这些计数只作观测，不作为“必须出现回滚”的证明。迟到帧重放由 04/05 的定向样例和复制器测试断言；快照失配由 05/06 的故障注入验收断言。

## 项目侧替换点

| 决策 | Tiny 的默认位置 | 新项目应替换的内容 |
| --- | --- | --- |
| 认证与进场 | 消费工程的 `TinyConsumerLobby.Enter`、`TinyProjectLaunch` | 账号、会话令牌、Gateway 地址、返回场景 |
| 规则和状态格式 | Logic 包的 `TinyBattle`、`TinyInput`、`TinyBattleStateCodec` | 输入语义、确定性状态、编解码与哈希；客户端和服务端共用同一份源码 |
| 服务端玩法 | `TinyServerGameplayModule.Create()` | Room 描述、同步模板、World 和 Battle 适配 |
| 客户端会话策略 | `TinyBattleSession` | 房间标签、输入提交、快照映射、恢复判据 |
| 输入与表现 | `TinyInputModule`、`TinyActorViewModule`、`TinyHudPresenter` | 控制方式、角色对象和状态展示 |
| Loading | `TinyAssetPreparation` | 有真实资源时注册资源准备步骤；Tiny 的程序化场地只验证启动清单 |

先运行完整门禁，再做 08 的规则变更练习。同步 schema 当前限定为版本 1；不兼容版本会在 `TinyBattleSession` 能力协商时拒绝，订阅、基线请求和输入均不应继续。`IncompatibleSchemaStopsBeforeSubscriptionAndInput` 是对应的定向证据。Loading 与战斗订阅还会校验启动清单哈希，防止客户端规则或场地标识与服务端不一致；修改规则时应同步升级共享 Logic 中的 `RulesKey`，此检查不代替同步 schema 协商。

服务端发布包中的 `composition/TinyCustomHost.csproj` 是仓库外可编译的组合入口。项目可在 `ConfigureGameplay` 注册自己的 `ServerGameplayModule`，并让该 Host 与同一发布包的 Gateway 配套运行；`-ServerBundlePath <目录> -UseCompositionHost` 可用真实 TCP 样例验证这条路径。

在仓库根目录用 [`./tools/publish-tiny-server.ps1`](../../../tools/publish-tiny-server.ps1) `-OutputPath <目录>` 生成独立 .NET 服务端包，先启动 `host/`，再启动 `gateway/`；定制组合工程时由自定义 Host 代替内置 Host。客户端消费工程与服务端包是两个交付物。仓库 Host 默认启用 Turn，可用 `AbilityKit__Tiny__EnableTurn=false` 关闭；只发布实时玩法时不必安装 Turn 客户端包。

消费工程的 `Assets` 不包含从源码工程复制的 DLL；Unsafe 由 OpenUPM 的 `org.nuget.system.runtime.compilerservices.unsafe@5.0.0` 提供。验收脚本检查依赖和 registry scope，并拒绝旧内嵌包及 `Assets` 下额外的 DLL。首次导入需从 OpenUPM 和 Unity Registry 获取公共包。

当前仓库没有 Tiny 的 CI workflow。开发者可在本地运行 `./tools/verify-tiny-starter.ps1 -SkipUnity` 检查 .NET 与 TCP 阶段，或运行完整命令，在隔离工程中以 `-batchmode -nographics` 执行 Unity 验收。每次运行在 `local/Logs/tiny-acceptance-*/phases.json` 记录实际运行或跳过的阶段；独立进程的 `process-{Mode}/owner.json`、`guest.json`，以及 Unity XML、JSON 和 TCP 日志保存在同一目录。完整门禁还产生 `unity-cross-{Mode}/` 证据，具体覆盖的模式以当次 `phases.json` 和目录为准。

正式项目代码只能存在一份；`Samples~` 里的章节脚本只负责演示公开 API 的装配，不能成为生产会话的隐式依赖。
