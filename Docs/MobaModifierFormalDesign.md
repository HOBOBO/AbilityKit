## 1. 结论与边界

现有 `AbilityKit.Modifiers` 适合作为数值计算内核；MOBA 层已有持续对象投影、来源清理、部分参数消费和回滚快照。它们不足以直接作为可铺量的内容模型。当前 `TargetKind=SkillParameter` 同时承载技能参数、子弹、发射器、Buff、AOE 和召唤参数；引用 ID 也被当作浮点数 Override。技能替换实际上属于槽位候选选择，不能通过数值修改器表达。

**核心不变量：只有处于 Active 的 `IContinuous` 实例，或绑定在该实例生命周期上的桥接，才能提供修改器效果。** 修改器定义、公式、槽位候选和参数目录都是惰性配置；Trigger、装备、升级与消费适配器不能独立写入生效集合。Pause/End 后，该实例提供的所有效果必须不可见。桥接只是把已有领域对象接入 `IContinuous` 生命周期及投影协议，不能另建一套不受管理的来源生命周期。

**默认聚合边界是同一个效果 owner。** 对施法者的技能、发射器、子弹和 AOE 参数，相关持续行为向施法者 owner 提供效果；Buff 作用于目标时，向目标 owner 提供效果。发射器/子弹/Buff 等名称首先是参数记录中的领域与实例上下文，不自动意味着要新建一个修改器存储作用域。对象确实成为独立效果承受者时（例如召唤 Actor 自身属性、可被修改的子弹实体），才给它建立自己的 owner，并显式定义创建、销毁和血缘转移。一个解析请求只在一个明确的效果 owner 下聚合，避免隐式跨 owner 合并。

正式版分为三个效果类别，统一由持续行为提供，分别定义运算：

| 能力 | 目标 | 求值方式 | 结果 |
|---|---|---|---|
| 属性修改 | 一个 Actor 的属性 ID | 有界数值表达式 + 属性聚合规则 | 数值 |
| 技能槽位选择 | `(Actor, Slot)` | 对有效候选排序并选择一个 | 整数 Skill ID |
| 领域参数修改 | 一个对象/动作在特定阶段的参数 ID | 类型化数值聚合或引用选择 | 整数、浮点数或引用 ID |

`ModifierData` 和 `ModifierCalculator` 只参与数值计算。技能槽位候选、配置引用选择、生命周期绑定及阶段快照由 MOBA 领域服务负责。消费适配器只在领域规定的阶段读取有效效果，并写入本次请求或实例状态；它不是通用对象 getter/setter。新增领域参数需要明确消费点和生命周期来源，不需要为每个技能或每个参数新增组件。

## 2. 当前实现的扩展障碍

本节保留方案制定时的结构性问题清单；其中部分入口和消费链已在后续阶段迁移。判断当前放量状态以文首验收更新和路线图为准。

1. **优先级没有稳定的业务含义。** `MobaSkillParamModifierService` 调用默认 `ModifierCalculator`。`OperatorComposer.Compose(..., strategy)` 在策略为 `null` 时直接进入默认组合器，跳过排序；默认组合器遇到第一个 Override 就结束。因此在 MOBA 当前路径上，Override 由写入顺序或作用域链顺序决定，不保证按 `ModifierData.Priority` 选择。核心库其他入口会排序，且排序约定为较小的数值优先；不应依赖它实现“优先级高的技能生效”。
2. **技能替换发生得太晚且目标不对。** `MobaSkillLoadoutService` 读取槽位中的基础 ID，`SkillCastCoordinator` 只对普通攻击在施法入口修改 ID。`SkillCastPreparationService.ResolveSkillLevel` 与 `MobaSkillRuntimeAccess.TryGetActiveSkill` 要求槽位运行时的 ID 等于施放 ID；替换后等级、冷却和充能可能找不到所属运行时。技能按钮、输入校验和选技也未共享同一次选择结果。
3. **参数目录是键目录，不是消费契约。** `modifier_parameters` 有 Domain、ValueKind、OpMask、ResolveAt，但运行时仍在各 PlanAction/Service 手工调用 `ResolveXxx`。目录行不能证明阶段真正消费了该键，也不能描述对象身份、读取链、合法范围、是否允许活跃对象更新。
4. **owner 与阶段记录混合。** `MobaModifierOwnerScope` 已列 Actor、SkillRuntime、Launcher、Projectile、Summon，但生产触发动作和持续投影主要写 Actor；发射器与角色链仅用于部分发射参数。若把每种领域对象都当成修改器存储 owner，需要额外处理多作用域合并、释放和 ID 复用，且仍无法说明一个 Actor 增益何时影响已创建对象。应先把对象实例与模板 ID 放进阶段记录，在同一效果 owner 下筛选；仅对真正独立承受效果的对象创建新 owner。
5. **数值来源不足以表示常见公式。** `MagnitudeSource.Attribute` 只支持单属性乘系数；`ContextFloat` 使用字符串键，`Pipeline` 在 MOBA DTO 转换时退化为固定值。`MagnitudeBaseValue=0`、`MagnitudeCoefficient=0` 又被当作“未填写”，无法区分有意的零。跨 Actor 属性、多个属性、等级和上下文的组合缺少受约束的配置形式。
6. **叠层与实时依赖未形成统一语义。** 当前投影通过修改 `Magnitude.BaseValue` 处理层数，快照在首次投影捕获；属性来源实时引用没有完整失效通知。不同操作对层数的含义不一定相同，尤其是 Override、Mul 和 PercentAdd。
7. **仍存在绕过持续行为的写入口。** `AddSkillParamModifierPlanActionModule` 直接调用 `MobaSkillParamModifierService.AddFixed`，移除动作直接按作者填写的 `SourceId` 清除。两者没有与 `IContinuous` 的暂停、结束和重建绑定。现有 `MobaContinuousLifecycleBinder` 已有激活/恢复投射、暂停/结束清理的主路径，但 `ModifierSourceId` 仍由各配置提供，缺少统一的实例身份与写入权限约束。
8. **实例键和回滚尚未形成单一权威。** Pipeline 与 TriggerInterval 持续实例用 32 位哈希生成 `ModifierSourceId`，投影器按该整数清理，同 Owner 下的碰撞会导致错误撤销。参数服务还能独立保存/恢复效果条目，而持续捕获回滚只按当前已存在的实例身份匹配并重投射；这些机制需要明确恢复顺序和一致性检查，不能把“有快照”视为完整的持续实例恢复。

这些是结构性结论。已有的导表通过和少量示例行为，不能证明新增大量参数、来源和生命周期组合后仍一致。

## 3. 公共记录与生命周期

每个提供效果的 `IContinuous` 实例持有一个运行时投影身份，至少能区分 `World/ContinuousInstanceId/Generation`，并记录效果 owner。它由持续行为管理器分配或从其稳定实例身份派生；配置模板 ID、Trigger 作者填写的 ID 和独立的 `SourceId` 都不能充当生命周期权威。一次 Buff、一次技能施法、一个发射器持续实例分别拥有不同投影身份，但可以共同向同一个效果 owner 提供效果；重新生成的实体即使复用整数 ID，也不能继承旧投影。取消投影必须幂等。现有 `ModifierSourceId` 是迁移期存储键，正式版需验证其与持续实例一一对应，且不能被外部动作伪造。

一条投影记录至少包含：`DefinitionId`、目标类型与目标 ID、所属持续实例身份、优先级、同优先级顺序号、操作、数值来源或引用值、捕获策略、叠层策略。顺序号由稳定配置顺序及实例序号组成，不能依赖字典遍历或网络到达顺序。候选选择和数值聚合都必须显式声明“优先级数值越大越优先”；迁移旧 Priority 时做一次映射，不暗改既有数值效果。存储层仅接受生命周期投影器的写入；公开查询 API 不返回可写集合。

生命周期统一为 `Register -> Activate -> Pause/Resume -> End -> Unregister`。Activate 投射，Pause 撤销，Resume 用同一持续实例和捕获策略重投射，End/Unregister 幂等清理。层数或配置变化通过该实例的 `Reproject` 原子替换投影；失败不得留下半套效果。回滚先恢复持续实例及其状态、身份和捕获值，再重建投影视图；投影视图不能单独恢复成一个没有活跃持续实例的效果。阶段快照属于创建出的对象或动作请求，后续持续实例结束不追溯修改已发射子弹或已提交的施法，除非该参数明确声明支持活跃更新。

**桥接契约。** 已有 Buff、技能 Flow、发射器或其他领域对象若本身不是 `IContinuous`，可以用一对一的桥接实例承接 `IContinuous` 生命周期。桥接必须有明确的领域拥有者、建立/刷新/结束事件、暂停语义、稳定实例身份及回滚重建入口；桥接注册到同一个 manager，并由同一 binder 投影。一个桥接不能凭目标 Actor ID 推测自己仍然存活，也不能把领域对象销毁后的效果留在存储中。桥接若无法处理 Pause/Resume、销毁与回滚，就不能作为正式修改器提供者。纯瞬时动作只可请求创建、刷新或终止持续实例；需要在同帧短暂生效的效果，也要显式定义该实例跨越的提交阶段并在阶段结束后终止。

常驻天赋、装备与肉鸽局内升级分别由角色生命周期、装备持有期或本局升级持有期的持续实例承载；“永久”只表示这个持续实例的结束条件较晚，不表示写入永久生效记录。角色死亡、装备卸下、升级重置、对局结束和回滚重建都必须走该实例的结束或恢复流程。多份升级要明确是多实例叠加、同一实例叠层，还是互斥刷新，不能靠重复 `AddFixed` 的次数隐式决定。

## 4. 属性修改与公式

属性目标固定为 `(TargetActor, AttributeId)`；数值来源的 Actor 角色必须显式选择 `Owner`、`Source`、`Target` 或经领域上下文解析的 `Caster`。取值还需选择 `BaseAttribute`、`FinalAttribute` 或当前资源比例，禁止用同一字段含混表达。Buff 加在受击者身上时，`Owner` 是受击者，`Source` 才是施加者。

第一版公式使用有界、可静态校验的表达式树或后缀指令表，不执行任意 C#、脚本或字符串 `eval`。建议节点：常数、属性引用、技能等级、白名单上下文值、`+ - * /`、`min/max/clamp`、条件选择。公式结果是一个“修饰量”，再交给 Add、PercentAdd、Mul 或 Override 聚合；例如 `100 + Source.PhysicalAttack * 0.4`，或 `Target.MaxHp * 0.02 + Level * 5`。除法零值、非有限数、缺失上下文、精度和舍入必须在契约中定义并由导出器/运行时拒绝或采用声明的回退值。

`OnApplySnapshot` 在持续提供者首次激活时读取所需属性和上下文，将结果保存在该实例中并用于暂停恢复与回滚。`OnEventSnapshot` 在指定阶段对仍 Active 的提供者重新读取。`Realtime` 只能用于有依赖图和变更通知的属性：编译公式时提取依赖，拒绝直接/间接循环，属性或资源变化后按确定顺序标脏重算；没有该链路时不允许配置实时公式。首次交付可只开放前两种快照策略。

公式编译和数值计算必须使用一个明确的战斗精度规范。既有通用内核以 `float` 计算，而 MOBA 的计时、资源等路径已采用定点值；正式版需决定在计算边界量化为统一定点值，或证明当前浮点运算在目标平台的回放结果一致。所有常数、属性读取、运算中间值、舍入与最终写入遵循同一规则；禁止 NaN/Infinity 进入快照。该决定应先于公式表铺量。

叠层策略按定义显式选择 `ScaleMagnitude`、`RepeatContribution`、`HighestStack` 或 `NoStack`。Override 默认 `NoStack`；PercentAdd 的线性叠加与逐层复合是两种不同策略。Buff 层数变化时按策略重投射，不能统一乘 `BaseValue`。

## 5. 技能槽位候选

基础装配提供每个槽位的默认候选。Buff、装备、被动或阶段效果由对应持续实例向 `(Actor, Slot)` 投影候选记录：`SkillId`、`Priority`、可选资格条件、提供者实例身份和稳定顺序。选择器先过滤已失效/不合法候选，再按 `Priority` 降序、提供者类型顺序、配置顺序和持续实例 ID 作确定性排序；取第一项。无有效候选时回到基础装配。这里不执行 Add/Mul/PercentAdd，也不通过 `float` 保存 Skill ID。

槽位候选的资格条件只可引用 Slot、基础 Skill ID 和选择前已确定的状态；不能引用“最终选中 Skill ID”来决定自己是否入选。后续数值参数的 Selector 若要匹配 Skill ID，必须显式选择 `BaseSkillId` 或 `EffectiveSkillId`。引用模板的替换也按先后顺序处理：先选 Launcher/Projectile 模板 ID，再以选出的 ID 匹配其数值修改器，避免选择条件环。

选出的结果应为 `ResolvedSlotSkill { Slot, BaseSkillId, EffectiveSkillId, ProviderContinuousId, Revision }`，供技能按钮、输入、AI、施法准备和诊断共用。直接按 ID 触发的派生技能不经过槽位候选。一次施法在准备时锁定 `EffectiveSkillId`；提供者随后暂停或结束只影响下一次施法，正在执行的 Flow 保持原 ID。

槽位运行时持有等级、充能和默认冷却状态。正式版必须选定冷却归属，建议首版采用 **槽位共享冷却/充能，变体继承槽位等级**；不同技能独立冷却需要单独的显式组 ID 与状态容器。经济结算按槽位运行时取状态，施法内容按锁定的有效 Skill ID 取配置。现有 `TryGetActiveSkill(slot, skillId)` 的严格相等条件需随迁移调整，且 UI、技能升级、回滚和重连读取同一槽位结果。

## 6. 领域参数与阶段

参数目录每行是一个稳定的 `ParameterId`，同时声明 `Domain`、`Field`、`ValueKind`、`AllowedOps`、`OwnerRole`、合法记录字段、`ResolveStage`、`CapturePolicy`、`ValidationPolicy` 和消费适配器 ID。数值、枚举与资源引用分别走不同的类型化通道；引用值使用整数 ID 和对应表的外键校验。参数目录是 authoring schema，运行时由注册的领域适配器消费，不能靠 Key 名推测行为。`OwnerRole` 决定本次效果在哪个 owner 下聚合，例如施法者或 Buff 承受者；领域对象的实例 ID 用于筛选，不默认成为第二个 owner。

| 对象/阶段 | 建议可修改内容 | 生效边界 |
|---|---|---|
| 技能准备 | 资源消耗、冷却、施法范围等 | 本次施法快照；查询与结算读取同一结果 |
| 发射器创建 | 发射器类型/ID、重复次数、间隔、总时长 | 创建时快照，并写入发射器运行时 |
| 每轮发射 | 每轮数量、扇角、散布、该轮速度 | 每轮以施法者 owner 和本次 Launcher 记录读取活跃投影 |
| 子弹生成 | 子弹 ID、速度、生命周期、命中冷却、返回参数 | 每颗子弹快照；活跃轨迹变更另设专门能力 |
| 命中/周期事件 | 伤害参数、命中目标数量、周期触发间隔等 | 由事件或领域运行时在明确阶段读取，不回写静态配置 |
| AOE 生成 | 半径、时长、延迟、周期 | 生成快照；半径实时变化需要碰撞体同步与回滚支持 |
| 召唤创建 | 召唤物 ID、数量、寿命、属性继承比例、等级 | 创建快照；创建后属性修改走召唤 Actor 属性通道 |
| Buff 施加 | 时长、初始层数、周期 | 施加/刷新时快照；既有 Buff 的即时调整使用独立动作 |

每次消费明确一个效果 owner 和一份阶段记录，例如“每轮发射：施法者 owner + SkillCast/Launcher/本轮序号/所选模板”。同一 owner 下的全部活跃持续投影按参数地址与记录字段筛选后统一聚合。Buff 承受者、召唤 Actor 等确需改变 owner 的边界由领域流程明确传递，不在解析器中隐式遍历 `Launcher -> SkillCast -> Actor` 链。迁移期可兼容现有 owner-chain API，但新内容不依赖它表达来源优先级；对象尚无稳定身份时也可以修改创建请求，只需阶段记录具备相应模板和来源上下文。

活跃持续实例的投影按目标参数维护有序视图与版本号；实例激活、暂停、结束、层数和依赖变化时更新版本，消费阶段读取稳定快照。热路径不能每发射一颗子弹就遍历全部持续对象、分配数组并排序。若读取期需要合并多个作用域，应使用有界的无分配合并，并对最大活跃投影数、公式节点数及递归深度设发布上限。诊断解释可按需构建完整提供者列表，不参与战斗热路径。

参数有效性分为静态检查和最终值检查。导出器检查类型、单位、引用表、合法操作和阶段；消费适配器检查本次最终值，如数量正整数、半径正数、时长的零值语义。最终值不合法时返回可诊断失败，不能在不同消费路径中一处静默钳制、一处抛异常。

## 7. Excel 与发布方案

现有 `修饰参数` 的旧 1-16 号 ID 已按 [修饰器配置契约](MobaModifierAuthoring.md) 一次性迁入领域区间，旧号停用；运行时 `ModifierKey` 键位和值类型保持不变。迁移脚本同步更新引用并记录旧新映射；新增列/表应填充默认值，并保留旧字段作为过渡读取。建议拆成以下编辑实体：

| 表 | 内容 |
|---|---|
| `修饰参数` | 领域字段、值类型、owner 角色、阶段记录字段、消费适配器、范围与引用契约 |
| `数值公式`、`公式节点` | 可复用的有界表达式及属性/上下文依赖 |
| `数值修饰定义` | 参数或属性目标、操作、公式/固定值、优先级、捕获与叠层策略 |
| `技能槽位候选` | 槽位、整数 Skill ID、优先级、资格条件 |
| Buff/持续流程/升级持有者绑定 | 引用定义 ID，由其 `IContinuous` 实例或生命周期桥接提供效果 |

已发布 `ModifierTemplate.Id` 与 `ModifierParameter.Id` 继续稳定。当前 `TargetKind=4` 的领域数值条目可自动迁到数值修饰定义；`Skill.SkillId` 以及其他引用 ID 不应迁成数值公式，而应进入类型化引用选择或技能槽位候选。兼容加载只用于迁移，不允许新内容继续写旧的浮点引用字段。

导出时生成参数注册表及消费适配器清单。每个启用参数必须有一份明确的消费语义，并列出所有实现路径；普通 Shoot 与发射器路径可以共享同一个速度语义，但同一次子弹生成只能应用一次。若不同路径的阶段或基础值不同，应拆成不同参数地址。缺失消费路径、值类型不匹配、公式循环、非法作用域、引用不存在、未定义零值语义、Priority 越界，或找不到持续行为/桥接绑定的效果定义，均应阻断发布。Trigger Authoring 的动作应选择持续过程或升级实例定义，并从同一目录选择该实例所引用的修改器；不维护第二份参数 ID 列表。

`add_skill_param_modifier`/`remove_skill_param_modifiers` 是迁移债务，不作为正式版作者接口。迁移时把一对直接写入/清除动作改为“创建或刷新持续提供者/按该提供者身份终止”，参数、操作和值放在提供者引用的修改器定义里。对原来仅有 `SourceId` 的内容，先逐条确定拥有者、结束条件和重复触发策略；无法确定生命周期的行标为迁移阻断，不能靠旧 `SourceId` 推定归属。完成内容迁移后，删除或内部化服务的公开写入口，并以发布检查禁止新内容使用旧动作。

## 8. 实施顺序与验收

实施优先级和放行条件见 §14。先冻结旧配置的 Priority、同级决胜、数值聚合、捕获与层数行为，并保持已发布 ID ABI；随后关闭持续行为以外的写入口，打通同 owner 的阶段记录与真实发射链。槽位候选和属性公式建立在这条链路之上，再逐领域扩展参数目录。实时依赖与活跃对象更新必须独立验收后开放。

正式版验收至少覆盖：同一 owner 下两个持续实例的高低优先级及同级决胜；Pause/End 后效果消失、Resume 后按策略恢复；桥接拥有者销毁与 ID 复用无泄漏；撤销最高槽位候选回退；换技能期间等级/冷却/充能一致；多属性公式的 Source/Target 捕获、叠层和回滚；发射器跨多轮的快照与事件采样边界；子弹、AOE、召唤物的阶段记录传递及 owner 切换；Unity 与 Console 导出一致；确定性重放与诊断视图显示持续实例、基础值、各条贡献、阶段快照和最终值。还要验证触发动作及其他公开 API 不能绕过持续行为直接提供效果。只有这些端到端用例通过，才能把对应领域标记为“可铺量”。

## 9. 大量参数的统一寻址模型

肉鸽升级常常是“本局所有子弹速度 +20%”“仅二技能生成的子弹 +2 颗”“某类命中的范围增大”。同一个 owner 可以持有这三种效果，靠参数地址和阶段记录区分。正式版一次读取需要四个独立维度：

| 维度 | 作用 | 示例 |
|---|---|---|
| 参数地址 `ParameterId` | 指明业务字段及类型 | `Projectile.SpawnSpeed`、`Damage.BaseDamage` |
| 效果 owner `OwnerRef` | 指明聚合属于哪个效果承受者 | 施法者 Actor、Buff 承受者 Actor、召唤 Actor |
| 阶段记录 `ParameterRecord` + `Selector` | 携带并匹配本次业务上下文 | 槽位、Skill ID、Launcher/Projectile 模板与实例 ID、Action 节点 ID |
| 消费阶段 `Stage` | 指明何时从基础值生成结果 | CastPrepare、LauncherCreate、Emit、ProjectileSpawn、Hit、AreaSpawn |

`OwnerRef` 与 `Selector` 不可互相替代。同一施法者 owner 下，一个持续实例可以只影响槽位 2，另一个可以只影响 Launcher `L1` 之后生成的子弹。它们并不需要分别写入 SkillRuntime、Launcher 或 Projectile 容器。`Selector` 首版只支持可索引的等值/集合条件及稳定标签：Slot、BaseSkillId、EffectiveSkillId、LauncherTemplateId、ProjectileTemplateId、AreaTemplateId、SummonTemplateId、TriggerId、ActionNodeId、DamageReasonKind。字段是否存在由 Stage 定义；例如 `Hit` 可以读取目标和伤害原因，`CastPrepare` 不能假装已经有 Projectile 实例。复杂动态条件交给 Trigger Authoring，在条件成立时创建、刷新或终止持续提供者，而非每次读取参数时解释任意谓词。

`ActionNodeId` 需要由 Trigger Authoring 为可修改动作持久分配，不能使用动作列表下标或 JSON 路径。对同类动作有两种合法粒度：“该技能的所有 `give_damage`”与“指定动作节点的 `DamageValue`”。不做此区分，技能内多次伤害会被一起放大，或编辑动作顺序后升级失效。

消费请求携带明确的效果 owner 与 `ParameterRecord`。记录的输入上下文只读，包含施法者、归因角色、目标、槽位、基础/有效 Skill ID、SkillRuntimeHandle、各临时对象实例与模板 ID、Trigger/Action 节点 ID、伤害原因和逻辑帧；解析结果写入单独的业务结果字段或返回值。领域流程在创建发射器、子弹、AOE、召唤物时传递必要的血缘身份、模板选择结果和阶段快照；后续事件采样用记录到同一个效果 owner 查询仍 Active 的持续投影，不能把创建时的候选永久复制成活跃效果。记录需要有明确的字段可用性和复制/锁定规则，不能事后仅凭根 Actor ID 猜测技能、发射器或动作节点，否则多技能并行时会串用升级。

## 10. 类型、运算与公式层次

不把所有配置字段强制塞进 `float` 修改器。正式版按值类型提供以下操作：

| 类型 | 可用操作 | 不允许的操作 |
|---|---|---|
| 有单位数值（定点/整数） | Add、BasePercentAdd、FactorMultiply、BaseOverride、FinalOverride，以及声明过的上下限 | 未声明舍入的整数乘法 |
| 引用 ID（Skill/Projectile/Launcher/Area/Summon 等） | 按优先级选择一个有效整数引用 | Add、Mul、通过 `float` 转回 ID |
| 枚举/布尔模式 | 按优先级选择；必要时提供领域专属合并规则 | 把枚举数字当连续数值 |
| 列表、目标规则、命中策略、行为图 | 领域行为或完整策略模板的候选选择 | 对内部字段做无边界反射写入 |

数值层建议固定为：先选择最高优先级的 `BaseOverride`（没有则使用原始基础值 `B`），得到 `B'`；普通结果为 `(B' + sum(Add) + B' * sum(BasePercentAdd)) * product(FactorMultiply)`；最后若存在 `FinalOverride`，取其最高优先级的值。例：基础 10、Add 2、BasePercentAdd 50%、FactorMultiply 2，结果为 `(10 + 2 + 10 * 0.5) * 2 = 34`。各聚合层的定点舍入和最终范围检查必须固定，不能让写入顺序决定结果。`FinalOverride` 是明确的终止语义，不能把普通 ID 选择和数值 Override 混用。旧 `PercentAdd` 当前按各来源 `(1+x)` 连乘，旧配置须保留旧策略或显式迁移，不能直接改名后得到新数值。Priority 只决定相互竞争的选择/Override；可共存的 Add/Percent/Multiply 按声明的层次聚合。

公式只产生一条记录的修饰量，例如 `Source.Attack * 0.35 + Level * 4`，不自行寻找其他修改器，也不修改其他对象。参数聚合器负责把多条修饰量与基础值组合。这样公式可复用，升级来源可叠加，诊断也能分别解释“该来源算出多少”和“所有来源合成多少”。公式引用其他**最终属性**时必须构建依赖图；引用自己的最终值或形成跨属性环时拒绝发布。常用公式模板应覆盖固定值、等级成长、单属性系数、多属性线性组合、生命/资源比例和 `clamp`，其余按白名单节点扩展。

## 11. 消费适配器和内容创作

每个可修改参数应有一个明确的 `ParameterDescriptor`，至少声明稳定 ID、显示名/单位、值类型、允许操作、适用 Stage、合法 `ParameterRecord`/Selector 字段、效果 owner 角色、基础值提供方式、数值范围、零值语义、整数舍入策略、快照/更新策略、消费适配器和诊断标签。作者可以从目录知道“该参数到底改变什么、何时生效”。目录中的 `ResolveAt` 不能只作为说明文字。

运行时数据流是 `Continuous 持有定义 -> lifecycle binder 向效果 owner 投影 -> 领域流程传递 ParameterRecord -> 按 owner/参数/记录读取活跃投影 -> 领域流程写回本次请求或对象快照`。这里“写回记录”是本次业务数值的写入，修改器存储的增删仍只由持续行为生命周期驱动。类型化解析器负责按 owner 收集候选、用预编译 Selector 匹配记录、按稳定规则聚合并验证最终值；领域适配器在正确阶段提供基础值并应用返回结果。既不修改共享 `ProjectileMO`/`AoeMO`/Action 配置对象，也不提供任意对象字段的通用 get/set。一个阶段适配器可以解析该阶段的一组参数。可采用生成的 `ParameterId<T>` 常量和 `ResolveNumber/ResolveReference/ResolveChoice` 入口，避免字符串查找与装箱。底层 `ModifierKey` 继续可作数值计算键，但作者 ID 不应受其 Category/SubCategory 两个 8 位段的容量与分配方式约束。

“可修改”的基础值至少有四类，必须在目录中标识：Luban 模板字段、Trigger Action 入参、运行时计算结果、当前实例状态。前三类可以在消费阶段构建新请求；第四类需要由持续实例的活跃更新协议驱动领域命令（例如改变活跃子弹速度、重建 AOE 碰撞半径），不能自动套用创建快照。特别是 `give_damage` 的 `DamageValue` 在 Trigger Authoring，`AttackInfo` 又有 BaseDamage、DamageRate、FlatBonus、FinalDamage 等槽位。需要分别暴露诸如 `Damage.RequestedBase@Hit`、`Damage.PreMitigationBonus@DamageCalculate` 的明确参数地址，并保证每个效果只在一个层次应用一次，不能同时改 Action 入参与最终伤害而重复增益。

每新增一项普通数值参数，预期工作是：登记目录行、确认可由哪些持续提供者投影、在对应领域阶段绑定基础值与结果、增加消费及生命周期契约测试。只有新增一种**行为**（例如弹射、穿透、轨迹转向或命中策略）才扩展领域服务或策略接口；配置参数不应制造按英雄数量增长的代码类。

## 12. 阶段快照、活跃更新与性能

参数声明三种不同生效模式：`CreateSnapshot`（创建/提交时固定）、`EventSample`（每轮发射/每次命中重新取值）、`LiveProperty`（对象存在期间保持同步）。同一个“速度”在子弹生成和飞行中改变是两项不同能力：前者只影响未来子弹；后者还要处理运动积分、预测、碰撞、暂停和回滚。`LiveProperty` 只有注册了领域更新适配器、撤销方法和回滚快照才能开放。对肉鸽首版，绝大多数参数采用前两种模式即可支持大量升级组合。

读取顺序必须确定：先从有效持续投影选择引用模板，再读取所选模板的基础值，再在该阶段应用数值修改，最后创建实例。每轮发射或命中重新采样时，读取的是该轮/该次的原始基础值与当前 Active 的持续提供者，不能把上轮结果作为新基础值，避免重复累乘。持续实例在同一帧的激活、暂停、结束按战斗命令顺序提交；一个阶段读取看到的是完整提交后的版本。Pause/End 只影响之后的采样；已形成的创建快照保持不变，除非有专门的活跃更新协议。

投影视图至少按 `(OwnerRef, ParameterId)` 分桶，再用编译后的 Selector 匹配 `ParameterRecord`；每条索引记录必须反向关联一个持续实例，以便 Pause/End 原子撤销。可按常用模板 ID/槽位建立次级索引。高频读取使用有界缓冲区或池化，避免每颗子弹排序与分配。版本号用于缓存已筛选的活跃投影集合，缓存键包含效果 owner、Selector 所需的模板/槽位/Action 节点和阶段；公式引用的实时数据不能误复用旧结果。发布器限制单持续实例投影条数、单 owner 活跃条数、公式深度与节点数；性能门槛按典型肉鸽高弹量场景测量 CPU、分配和快照大小。

## 13. 肉鸽升级贯穿示例

设角色拥有二技能 `S2`，发射器 `L1`，子弹 `P1`，命中后生成区域 `A1`。四项升级各由一个本局持续实例承载，都投影在该角色的效果 owner 下；`L1`、`P1` 和 `A1` 是传递记录中的筛选信息。下表只列它们投影的效果：

| 升级 | 地址与 Selector | 阶段 | 预期结果 |
|---|---|---|---|
| 双弹 | `Launcher.CountPerEmit`，Slot=2、Launcher=L1，Add 1 | Emit | 此后二技能每轮多一颗；其他技能不变 |
| 强击 | `Damage.RequestedBase`，Slot=2、Projectile=P1，公式 `Source.Attack * 0.25` | Hit | 每次命中按声明的属性快照时机增加伤害 |
| 扩散 | `Area.Radius`，Area=A1、来源 Skill=S2，BasePercentAdd 0.3 | AreaSpawn | 新生成区域半径增大；既有区域不变 |
| 变体 | `(Actor, Slot=2)` 提供 SkillId=S2B、Priority=100 候选 | CastPrepare | UI、施法、等级和冷却一致选择 S2B；提供者结束后回到 S2 |

升级来自常驻天赋时，由覆盖本局的持续实例提供；来自限时 Buff 时，由 Buff 的 Active 期提供；来自一次施法时，由 SkillRuntime 持续实例或一对一桥接提供。以“双弹”为纵向验收：激活升级实例后实际多生成一颗子弹；Pause 后下一轮回到基础数量；Resume 后再次多一颗；End 后恢复基础数量。已生成子弹继续使用生成快照；回滚到四个阶段中的任一个，再重放应得到同样子弹数量与运动结果。示例还需验证升级顺序任意、两份升级叠加/互斥、同帧多个发射器、换技能后旧子弹继续命中、重连后选择一致，以及桥接拥有者销毁时没有残留投影。它比只断言 `ResolveNumber` 的单元测试更能代表“可铺量”。

## 14. 按优先级推进

| 优先级 | 工作与交付 | 放行条件 |
|---|---|---|
