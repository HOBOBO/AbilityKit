# MOBA 英雄技能制作成熟度评估

> 评估日期：2026-10-30  
> 文档类型：阶段性工程评估与文档治理约定，不是新的配置权威来源。  
> 当前判断：**制作框架与发布流程已有较成熟骨架；端到端内容验证和跨系统契约尚不均衡，不能据此宣称整个英雄技能制作体系已全面稳定。**

## 1. 评估范围与口径

本评估回答两个问题：

1. 新英雄能否按现有流程稳定地从机制需求走到生产配置、运行时结果和验收？
2. 流程发生变化时，怎样避免所有英雄需求文档都复制同一套流程后再批量修改？

判断依据是截至评估日期可见的技能制作规范、生产流程文档、能力矩阵、英雄验收覆盖清单和测试门禁配置。它不是对所有 MOBA 源码、全部生产表和全部 Unity 测试逐项重跑后的审计。能力矩阵记载的源码事实有独立基线日期，使用前必须按当前消费者复核。

本文件使用以下证据等级，避免把“代码存在”误读成“英雄制作已稳定”：

| 等级 | 证据 | 能支持的结论 |
|---|---|---|
| E0 需求定义 | 规则和边界已明确，版本与数值来源可追溯 | 知道要实现什么 |
| E1 运行时机制 | 机制由通用服务/组件实现，并有针对性运行时测试 | 代码具备部分能力 |
| E2 作者化与发布 | 权威编辑源、序列化、编辑器校验、发布器和一致性检查连通 | 作者能通过规定工具发布 |
| E3 生产内容 | 至少一个真实生产配置组合消费该能力，发布检查通过 | 能力可被内容实际使用 |
| E4 英雄端到端验收 | 从输入/事件经过生产配置到真实战斗结果；涉及生命周期时覆盖中断和回滚 | 当前英雄路径有可重复验收证据 |

评级针对每个具体能力逐项给出；某个相邻等级的证据不能替代下一等级。例如 E1 单测不能证明编辑器发布可用，E2 可导出也不能证明配置产生了预期战斗结果。

## 2. 当前成熟度判断

| 维度 | 当前判断 | 证据与限制 |
|---|---|---|
| 生产配置权威源 | 较成熟 | 技能规范和 `Docs/MobaSkillPipeline.md` 已区分 Luban、Skill Flow、ActionEditor、Trigger Authoring、状态机 Authoring 的编辑源及发布物，并给出发布顺序。新内容可据此找到入口。 |
| 工具与编辑器链路 | 中上 | 多条链路已有 Authoring、导出和 Check；但矩阵中仍存在“代码/DTO/单测已覆盖，生产 flow 未使用”或“无配置样例”的能力，编辑器可编辑不等于内容作者已经完成端到端制作。 |
| 配置组合与生产实践 | 中等 | 已有多个英雄真实配置和验收样例；覆盖不是全机制，也不说明每个机制都有生产用法。每项需求必须核对生产数据，不应只看示例英雄数量。 |
| 发布一致性 | 中上 | Pipeline、Trigger、状态机和 Luban 有相应发布/检查步骤；发布物一致性是可操作的。流程变更仍可能影响多个编辑源之间的调用次序，必须由生产流程文档统一维护。 |
| 端到端英雄验收 | 中等偏弱 | `tools/moba-hero-acceptance-coverage.json` 登记 9 名英雄，各自只有 `repeatedRelease/buff/projectile/area/presentation` 五个粗粒度键；截至本评估，重复释放和 Buff 均为 covered，Projectile 7/9、Area 6/9、Presentation 5/9。该账本不能表示助攻归属、目标分类、施法实例去重、法术护盾等细粒度语义。 |
| 回滚/同步与生命周期契约 | 不均衡 | 部分实体和机制具备快照/回滚路径；能力矩阵仍列出关系状态、区域/实体生命周期等契约风险。能力矩阵事实基线为 2026-09-14/15，当前任务不能直接把其中条目计作现状，须追踪当前实现与消费者。 |
| 门禁反馈 | 中等偏弱 | 有英雄级 Unity EditMode gate 和覆盖 manifest 校验；当前 9 个英雄 gate 中 7 个 scheduled-only、2 个 PR 运行，均未配置 push 运行。Manifest 与 validator 采用固定英雄清单；新人接入需要维护多个登记点，遗漏会导致门禁账和文档脱节。 |
| 文档可维护性 | 有明确风险 | 技能规范、Pipeline/Trigger 生产文档是流程来源；英雄分析文档又会列出生产阶段与检查命令。若每份文档复制命令、目录、注册步骤或当前能力判定，流程调整会造成多处漂移。 |

**结论：**现有体系足以支撑按流程逐个实现英雄，也足以复用已经达到 E3/E4 的能力；对尚未达到端到端证据的机制，需要先做能力核验和试点，不能把矩阵结论或“已有扩展点”直接当作稳定承诺。当前更准确的状态是“流程骨架成熟、能力证据分层不齐、自动回归覆盖不足”。

## 3. 当前流程的主要稳定性风险

### 3.1 能力矩阵不是实时状态面板

`21-SkillCapabilityGapMatrix.md` 的事实基线是 2026-09-14，重验章节记录到 2026-09-15。它的分类、代码路径、生产使用计数和编辑器结论都可能被后续改动改变。总索引与技能规范对矩阵的描述也可能先于矩阵事实更新。

处理方式：新英雄开工时只把矩阵当作待核清单。对会影响设计的能力，记录当前运行时消费者、作者化/发布入口、生产样例和测试证据；若与矩阵不符，先修正矩阵的对应行与基线日期。不要因为矩阵写了“✓”就跳过 E3/E4 验证。

### 3.2 验收账本覆盖维度过粗，新增英雄维护点固定且分散

目前覆盖账的五个常用能力键仍较粗；例如“Projectile covered”不能说明 R 是否忽略非英雄并继续飞行，“Area covered”不能说明一次施法中的多个区域是否对同一目标去重。2026-10-30 已完成第一阶段治理：validator 不再维护预期英雄/fixture 硬编码数组，而是遍历 coverage manifest、从验收目录发现 fixture，并接受可扩展的 lower camel case 能力键；它继续校验英雄 ID/名称/fixture 唯一性、fixture 源码、coverage 状态以及关联 gate。

新增英雄现在仍需在 manifest 登记 fixture 和 gate，并在 `tools/test-gates.json` 定义相应 Unity 测试步骤；manifest 校验会检查三者是否连通。现有 gate 名单本身仍由 gate 配置维护，这是测试执行定义的权威来源，不再另复制到 validator。能力键可按需求细化，但具体用例应写入英雄 fixture/scene contract，不能用新增粗粒度布尔键替代行为断言。

2026-10-30 已完成第二阶段的最小证据链：coverage manifest 可选声明 `coverageEvidence`，把已覆盖能力映射到 fixture 中带 NUnit/UnityTest 标记的方法；validator 会检查方法真实存在且对应 gate 的 EditMode step 会执行该测试，并可用 `-ReportPath` 输出 `moba-hero-acceptance-evidence` 报告。当前 36 项历史 `covered` 能力中已有 35 项登记了来源方法，剩余 1 项是 Mozi 的 presentation，现有 fixture 没有明确的表现断言，报告标为 `missing-reference`。这表示待补证据而不是自动降级为未覆盖。该报告只证明引用和 gate 配置连通，不证明 Unity 测试已经执行通过；执行结果仍以 NUnit 工件为准。

下一步按报告逐英雄补齐 evidence，优先补金克丝和正在变更的英雄；证据方法应断言权威战斗结果，不能只断言 trace、动画或资源存在。只有当一个能力的生产配置、fixture 方法和实际测试工件都齐全时，才将其作为 E4 稳定复用能力引用。

### 3.3 P2 定时门禁不能替代开发期反馈

当前英雄 Unity EditMode gate 主要安排在 schedule 运行，策略说明在批量合入/发布前必须通过，但普通 PR 与 push 不会自动获得及时反馈。依赖开发者记住手动执行时，流程可用但回归保护尚未形成稳定闭环。

先为正在实现的英雄 fixture 建立本地必跑清单和结果工件，再按运行成本选择让轻量契约检查进入 PR、较慢的英雄 EditMode 留在 schedule 或发布门禁。没有实际 CI runner/执行证据前，不要把“已登记 gate”描述为“已自动阻断回归”。Coverage validator 已在 `moba-content-contracts` 中登记；英雄级 EditMode gate 的运行频率仍按 `tools/test-gates.json` 中各 gate 的 `ciPolicy` 判断。

### 3.4 机制扩展与玩法延期需要可追溯的契约

跨实体关系、按来源计数、单次施法共享去重、观察者视野、法术护盾和预测回滚，可能分别落在不同服务与快照边界。仅仅增加一个 Trigger 或参数不一定能满足确定性、生命周期和回滚要求。

每个需求差异至少说明：现有机制证据、缺失契约、扩展归属、快照/回滚责任、同帧顺序规则和验收方式。若本期不做，应明确记为延期玩法，并列出重开条件，避免表现资源或客户端效果被误称为权威机制。

## 4. 降低英雄需求文档的维护成本

文档按稳定程度分层，内容只在一个权威位置维护：

| 文档层 | 放什么 | 更新触发 |
|---|---|---|
| 制作规范与权威流程 | 配置归属、工具入口、发布顺序、检查命令、标签与通用验收规则 | 流程、工具或全局政策发生改变时更新；英雄文档只链接它 |
| 能力矩阵/机制契约 | 通用能力边界、能力证据、缺失契约、扩展归属与代表性 fixture | 通用机制、作者化能力或回滚契约变化时更新对应条目和基线日期 |
| 英雄需求文档 | 版本化玩法规则、英雄独有状态/参数、选用的通用机制、未满足差异、生产 ID 与英雄验收场景 | 只有该英雄规则、选择或证据发生变化时更新 |
| 发布产物与验收账 | 哪些配置发布、哪些场景已测、最近可追溯的测试工件 | 内容/fixture/gate 变化时更新，并由脚本校验引用 |

新增英雄文档建议采用稳定结构：

1. 规则版本、来源和待确认项。
2. 英雄机制到通用能力的映射，只记录本英雄的选择和差异。
3. 对每个关键机制标注 E0-E4 证据等级、当前证据链接和下一项验证。
4. 列出缺失契约、拟扩展层、回滚/确定性要求和延期范围。
5. 验收场景与结果；生产流程步骤只引用 `moba-skill-authoring`、`Docs/MobaSkillPipeline.md`、`Docs/MobaTriggerAuthoring.md` 和 Luban README。

英雄文档不应重复维护：编辑器菜单的完整注册步骤、Pipeline/Trigger 发布命令、跨英雄通用的回滚教程、全体英雄覆盖汇总、无版本时间戳的“当前支持”列表。若确需摘录便于阅读，应标明“摘要，权威来源为……”并避免复制易变命令与路径。

## 5. 将“稳定可复用”作为验收条件

某类通用机制达到以下条件后，才建议在后续英雄需求中作为稳定能力直接引用：

- 明确从权威配置源到运行时消费者的完整链路，并有发布一致性检查。
- 至少一条生产配置能使用该机制，避免只以 DTO、编辑器控件或单测证明可用。
- 有一个可重复的端到端 fixture，断言权威游戏结果，而不只是 trace、动画或 Prefab 出现。
- 机制涉及跨帧、临时实体、来源叠加或可中断流程时，覆盖结束、撤销、重复执行和回滚边界。
- 扩展后更新能力矩阵中对应条目及其证据日期；其他英雄文档不需要同步改写通用机制说明。
- 生产流程或通用契约变化时，只更新权威流程/契约文档，并通过链接让英雄文档继承变化。

达到上述条件的能力可以视为“已验证复用”；只达到 E1/E2 的能力应在英雄文档标作“待生产验证”，涉及未知回滚语义的能力应标作“需先定义契约”。

## 6. 对当前金克丝文档的应用

金克丝需求文档应继续保留英雄独有的 Q 武器模式与普攻联动、被动 takedown 参与归属、E 施法组去重、R 主次目标公式等差异。它不应独立成为第二份技能流程规范。

当前金克丝文档中列出的运行时入口均应视为待核/候选，直到具体生产配置和验收 fixture 通过。接入时优先登记细粒度验收场景，例如：

- Q：武器模式来源移除、普通攻击槽解析、切换时资源与攻速层规则。
- 被动：参与窗口、killer/assist 唯一归属、目标类别、重复 takedown 和持续时间刷新。
- W/R：首个有效目标、忽略目标后继续飞行、主次目标独立计算。
- E：三枚 Area 同帧重叠时的目标 claim 顺序、重复执行和 claim 集合恢复。
- 表现：动作/VFX 随权威状态和战斗事件重建，不由动画回调提交玩法结果。

## 7. 后续复核触发器

以下任一情况出现时复核本文的阶段性结论，而不是批量改写所有英雄文档：

- 配置权威源、发布顺序或发布器发生变化。
- 一个通用机制新增/改变回滚、同步、确定性或生命周期契约。
- 验收 manifest、validator 或 CI gate 改为自动发现/PR 必跑，或新增覆盖维度。
- 覆盖证据报告中出现大面积 `missing-reference`，或 evidence 方法与 gate 的实际执行策略不一致。
- 能力矩阵完成全量重验并更新事实基线。
- 新英雄端到端接入暴露出流程无法表达、无法发布或不可稳定验收的系统性问题。

其余情况下，只更新对应英雄文档的规则、差异或证据链接。这样流程与能力边界集中维护，英雄文档只承担英雄需求和验证事实。
