# 状态同步能力补全路线

本文承接 [D1 固定基线](13-StateSyncReplicationAndPredictionProposal.md) 和[提交顺序修复](14-StateSyncLayeringReview.md)。公网参考仅使用公开设计文档；运行与验证仅使用本仓库代码、协议和本机可控测试，不排查外部服务或非本仓库的网络字节。D1.1 与固定基线预编码复用已接入；视图和预测等其他运行时改造仍需单独确认。

框架包现状及抽象调整顺序见 [Source SDK 与 Colyseus 阶段评审](16-StateSyncPackageDesignReview.md)。

## 取舍

沿用 Colyseus [State Sync](https://docs.colyseus.io/state) 区分权威投影、全量和补丁的思路，以及 [StateView](https://docs.colyseus.io/state/view) 将观察者可见范围与全局世界分开的思路。AbilityKit 允许待发增量合并，不能把逐包应用的变化序列直接替换现有 `Delta(B, F)`。先让现有流的发布与恢复周期可解释、可测，再决定是否需要分观察者基线。预测边界见 [D2](13-StateSyncReplicationAndPredictionProposal.md)；不照搬整世界回滚。

## 已实现：D1.1 固定基线发布策略

**问题。** `BattleSnapshotSyncPolicy` 用两个绝对帧取模，4/30 的例行全量实际每 60 帧才碰到发布点；`BattleLogicHostGrain` 还直接传入 `max(1, TickRate / 4)` 作为主动刷新间隔。周期、恢复请求限频和 Observer 限速不能共用一个参数。

**实现。** 仅在权威状态同步模式启用相对周期：发布点仍由 `SnapshotIntervalFrames` 决定；例行全量改为距上次**通过整包预算的全量**达到 `FullSnapshotIntervalFrames` 后的第一个发布点。刷新请求仍合并，沿用 `max(1, TickRate / 4)` 作为独立的模拟帧阈值；首包和增量体积启发式保留。Host 记录全量触发原因和字节数，超预算候选不推进基线。Observer 继续负责交付预算和队列；旧订阅、附属状态推送、线协议、可靠事件、帧同步主链及共享世界逻辑不改。

**验收。** 4/30 从第 4 帧首次全量后，在第 36、68 帧例行轮换，不再等待第 60 帧。回归覆盖 1/30、低 TickRate、合并刷新请求、提前全量重置周期、整包拒绝后保留原基线及健康观察者不中断。验证结果见下节；大包欠额规则未改。

## 后续顺序

1. **D1.2 可见范围与节流**：先用测试数据度量共享基线的成本。需要 AOI 时，再设计视图/代际作用域，并区分离开视野与真正销毁；不提前添加逐观察者 ACK、字段掩码或动态降频。
2. **D2 局部移动预测**：先建立与权威快照同 Tick 的输入终结记录，再由独立对账器只重演本地受控移动。请求接受、帧同步确认、快照 ID、事件水位都不能代替输入终结；移动规则和固定步长可复用，时钟与恢复游标不合并。若线上更优先解决本地输入延迟，可独立评审 D2，不必等待 AOI。

## 已实现：权威状态同步固定基线预编码复用

- Host 复用固定基线整包预检的结果：仅在通过预算后把临时编码结果复制成独立副本，再推进流基线。超预算不分发、不推进基线，也不消费刷新请求。
- 仅权威状态同步的固定基线订阅走新的内部 Grain 调用，传递稳定载荷与帧号、全量标记、网络环境。观察者不再逐个编码，仍独立排队、限流和报告恢复。载荷在队列和 Gateway 发送链上按只读处理；不得改写、回收或与 codec 临时缓冲区共用存储。
- 旧订阅和帧同步附属推送保留原入口；Observer 不接管发布节奏。客户端线协议、可靠事件、帧同步主链和共享世界不变。内部新增 Grain 方法，部署时 Host 与 Observer 应同步升级；混版本滚动部署未验证。

[聚焦测试](../../../Server/Orleans/src/AbilityKit.Orleans.Grains.Tests/Battle/PreparedFixedBaselineDeliveryTests.cs) 的 6 项新增用例通过，覆盖模式分流、超预算不提交、旧订阅门禁、队列独立和 Orleans 本地 `DeepCopier` 保持同一个封装引用。相邻回归 50 项，49 项通过，已知大包欠额用例 1 项仍失败。本轮不解析、不解码载荷，也不抓包；没有测跨 Silo 传输、实际跨进程复制量或生产端到端开销。上节夹具的性能结果不能替代这些测量。

## 框架包：本地检查点接入与保留策略

[`world.statesync` 接入指南](../../../Unity/Packages/com.abilitykit.world.statesync/Documentation~/StateSyncDesign.md) 区分了通用帧缓冲、本地实体检查点、在线快照准入和预测重演。`StateManager` 的逐实体记录与网络快照分开是合理的；但 `CaptureState` 只给世界快照填元数据，随后调用 `GetFullState` 并不会得到完整的权威玩法状态。在线接入不应要求先装配 `StateManager`，也不应让它负责基线、导入或输入终结。

本批在不扩展公开 API 的前提下，按实际保留帧清理回滚记录，修复快照数与回滚记录数相同但帧集合不同的漏清。捕获在注册不变时复用注册视图；恢复只检查快照是否存在，不克隆未使用的快照。相关本地回归 39 项通过；未改网络、帧同步和共享玩法执行链，也未运行线上链路测试。

## 框架包：第二种类型化投影接入验收

[据点投影夹具](../../../src/AbilityKit.Network.Runtime.Tests/TypedObjectiveSnapshotIntegrationTests.cs) 直接把本地构造的据点归属和占领进度交给 `ClientSnapshotSyncPipeline<TSnapshot>`。夹具不依赖 MOBA Actor、网络、序列化或 `StateManager`。它是第二种投影的接入验证，不是新增玩法或生产消费者。

| 接入步骤 | 责任归属与注意点 |
| --- | --- |
| 映射流元数据 | 适配器填写世界、版本、序号、帧及基线标识。全量的 `BaselineFrame` / `BaselineHash` 要声明安装后供增量引用的基线，不能用零代替。 |

| 重建和应用 | 适配器按已提交的全量重建临时候选，不在上次增量结果上接着叠加。应用失败由回调报告（现有 `void` 回调通过抛异常）；管线不推进成功游标，也不发布成功结果，但不会补偿回调已写入的玩法状态。 |
| 提交和观察 | 应用回调正常返回后，管线提交接收游标并通知观察者。回调和接收由宿主串行安排；成功游标不代表输入已终结。 |

6 项新增用例通过，覆盖跳过一次增量后从全量重建、首份或轮换全量应用失败后可接受中间帧、增量失败后重试、错误基线请求及无效删除不留下部分视图。与通用准入、流状态机和管线的聚焦回归共 45 项通过。本批只增测试和文档，不解析载荷，不改变任何运行时行为。

**提取决策。** 暂不新增通用复制组件。现有管线已复用「校验 → 应用 → 提交 → 通知」；据点集合的增删和玩法导入应继续留给适配器。不能直接用该管线替换 MOBA：通用流用基线帧和哈希，同世界要求帧递增；其恢复标记保留到全量成功，但仍允许匹配旧基线的增量。MOBA 按流代际和精确快照 ID 判定，失配后要求新全量才恢复增量。若后续要统一，先评审这两类流的兼容策略和选项默认值，而不是先抽取实体集合或将预测纳入复制管线。

## 框架包：恢复策略与默认值（提案，未改运行时）

**建议默认：现有接入保持原行为；新接入若不能证明旧基线可以安全继续使用，显式选择严格恢复。**「请求全量」是给会话适配器的动作；「等待全量期间是否接受增量」是快照准入策略，两者独立。严格恢复不是要求逐条接收增量：每条增量独立引用同一份全量时，只要基线和顺序合法，仍可跳过中间增量。

| 场景 | 推荐处理 | 请求与解除条件 |
| --- | --- | --- |
| 中间增量未到，但当前增量仍可从已提交全量独立重建，且未违反显式序号限制 | 正常重建和应用，成功才推进快照游标。若已经进入严格恢复，仍拒绝该增量。 | 不因跳号新发请求；兼容策略下，成功增量也不解除既有恢复标记。 |
| 缺少基线、基线失配，或超过显式配置的序号限制 | 拒绝，不应用、不推进。兼容策略仍可接受此后匹配旧基线的合法增量；严格策略等全量。 | 发出 `FullSnapshot` 恢复意图；同一有效流内，只有全量成功应用并提交才解除。 |
| 重复、陈旧、旧代际，或不属于当前会话的世界 | 丢弃，不应用、不推进，不改变已有恢复状态。 | 不发请求；现有通用链的跨世界自动判定保留为兼容行为，不等同于新接入的错世界丢弃规则。 |
| 当前流的快照版本不支持 | 拒绝，不应用、不推进，报告兼容性错误。 | 新接入默认不因版本错误请求全量；由会话解决兼容问题。MOBA 现有准入返回版本错误时可请求全量，改变这一点须单独确认。 |
| 候选重建、应用或导入失败 | 不提交成功游标、不发成功通知。仅在确认基线仍可信、世界未被部分写入且失败可重试时，才重试该候选。 | 其余情况阻断增量、请求全量，成功重建并提交后解除。通用管线不会撤销适配器已写入的状态；MOBA 固定基线的应用或导入失败已进入全量恢复，保持不变。 |
| 会话显式换世界、换代或重连要求重建 | 由会话启动新作用域并废止旧流游标；只允许目标作用域的合法全量建立新基线。 | 已有订阅/重连流程承诺推送全量时先等推送，否则请求一次；响应被受理不算恢复完成。MOBA 导入路径还须完成可靠事件基线接管，才解除输入阻断。 |

### 当前值与建议默认

| 选项 | 当前行为 | 建议默认 |
| --- | --- | --- |
| 通用流门禁与序号 | 恢复标记不阻断仍匹配旧基线的合法增量；同世界要求帧递增；未配置序号跨度时不限制。兼容流允许跨世界全量，跨世界增量则请求恢复。 | 现有接入全保留。新接入显式绑定世界/流；无发布方序号跨度合同就不设硬上限，不把可跳过增量当作失配。 |
| MOBA 固定基线门禁 | `RequireFullBaseline()` 后拒绝增量；按流代际、精确基线与快照 ID 判定，模拟帧可相同、不可倒退。旧式准入的 `120` 模拟帧最大增量间隔不适用于固定基线。 | 保留严格等待全量和既有排序，不把 `120` 帧移植到固定基线或通用流。 |
| 恢复请求种类 | 通用管线默认意图是 `FullSnapshot`，不负责发送；MOBA 由会话执行恢复请求。 | 保留 `FullSnapshot`；接入时显式接线。若未接线，只能报告恢复意图，不能声称已发出请求。 |
| 客户端请求合并及重试 | SDK 信号去重窗默认 `1 秒`；MOBA 覆盖为 `0`，允许同优先级替换。MOBA 的代际任务预留追踪在途任务，但不是同一流仅一个在途请求的门禁；异常或拒绝会记录，并不在该恢复层自行定时重发。 | 兼容接入不变。若新增会话策略，同一会话代际、同一状态流默认至多 `1` 个在途全量请求；默认不启用定时自动重试。失败释放在途占用，后续合格恢复信号可再触发；真正解除仍以全量提交为准。不把去重窗当成退避。 |
| 服务端全量发布 | 周期全量间隔由服务端同步模板提供；MOBA 状态同步模板取 `30` 模拟帧，模板回退值也是 `30`。固定基线按距上次全量的帧数判断；请求触发的提前刷新门槛为 `max(1, TickRate / 4)` 模拟帧。 | 保留发布策略；周期全量、主动刷新门槛、Observer 交付限速和客户端重试分别配置，不共用一个时间参数。 |

**接入分工。** 准入层负责版本、顺序、基线和恢复门禁；重建层用已提交全量构造候选，不提前改基线；世界导入层负责候选校验与写入边界；会话负责全量请求、流作用域与恢复状态。未来的状态预测回滚只消费已成功提交的权威状态，按独立的输入确认与重演契约工作；快照游标不能当成输入确认，不借用帧同步的确认帧或恢复策略。固定步长、实体生命周期与玩法规则仍可由两条链复用。

**实施前确认。** 统一严格门禁、改变 MOBA 版本错误处理、加在途合并或定时退避，均不是本批变更。下一批可先用本地类型化夹具固定两条现状，覆盖失配后的合法旧基线增量、全量提交才解除、导入失败不提交，以及版本错误的现有差异；后续再分别确认行为变更。只用仓库源码和本地类型化数据验证，不抓包、不解析载荷。
