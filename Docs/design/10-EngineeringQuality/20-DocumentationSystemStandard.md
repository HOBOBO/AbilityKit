# 文档体系与维护规范

> 文档类型：Canonical 工程规范
> 事实基线：2026-11-24；本文建立文档维护要求，不表示历史文档均已完成核校。
> 适用范围：仓库共享文档与自有包文档；第三方文档保留上游说明和许可证。

## 1. 目标与权威入口

读者应能找到一项能力的接入方法、设计依据和实际限制，维护者应能确定该改哪一篇。每项契约只有一份权威正文，其余页面提供摘要与链接。

| 阅读目标 | 唯一导航入口 | 正文归属 |
| --- | --- | --- |
| 选择阅读路径 | [文档门户](../../README.md) | 只做分类和导航 |
| 安装、接入和使用某个包 | [包索引](../../../Unity/Packages/README.md) → 包根 README | 包内使用文档 |
| 理解能力边界和跨包协作 | [设计索引](../00-index.md) | `Docs/design/` 的对应权威专题 |
| 按步骤完成跨包任务 | [教程入口](../../tutorials/tiny/00-从这里开始.md)或对应仓库级指南 | `Docs/tutorials/` 或现有领域指南 |
| 查看提案、实施范围与历史决策 | [计划入口](../../../plans/README.md) | `plans/`；完成后将当前契约写回所属正文 |
| 修改或评审文档 | 本文 | 分工、模板、核校、维护与退役规则 |

本文维护文档制度；[治理路线图](../11-DocumentationCompletionPlan.md)维护实施顺序与历史记录；[首轮盘点](../../../plans/2026-11-24-DocumentationSystemInventory.md)记录指定日期的结构缺口。三者不互相代替。

## 2. 按读者与契约所有权分工

| 位置 | 应回答的问题 | 内容边界 |
| --- | --- | --- |
| 包根 `README.md` | 这是什么包？如何安装？第一步做什么？ | 定位、环境、依赖来源、最短接入路径、文档和样例入口、重要限制 |
| 包内 `Documentation~/` | 如何正确使用本包？ | 操作指南、公开 API 契约、局部对象模型、生命周期、故障定位、兼容和迁移 |
| `Docs/design/` | 为什么这样划分？多个包怎样协作？ | 能力地图、跨包所有权、装配与执行链、架构决策、失败与恢复边界、验证证据 |
| `Docs/tutorials/` | 如何一步步完成一个目标？ | 前置条件、连续操作、预期结果、故障定位；引用契约，不再定义契约 |
| `Docs/` 现有领域指南 | 在本仓库如何创作、运行、发布和验收？ | 跨包工作流、领域约束、工具链；沿用现有权威位置 |
| `plans/` | 为什么改？确认了什么？接下来怎么验收？ | 提案、方案确认、实施范围、里程碑和阶段结果 |
| `local/` | 本机调查过程与临时材料是什么？ | 草稿、探针和临时报告；运行报告放 `local/Logs/`，不提交 |

不能仅凭标题含“设计”就迁移文件。说明怎样管理一个公开对象的所有权，是包的使用契约；解释多个包如何交接所有权，是仓库设计。包内局部设计随包维护，仓库专题通过链接说明组合关系。

包使用文档必须在独立安装后可读：本地链接只指向包内已有文件，不依赖兄弟包、`src/`、仓库测试工程或 `tools/` 的相对位置。仓库集成与测试命令留在仓库指南。包版本、Unity 最低版本和依赖的声明来源为 `package.json`；重复摘录时注明来源并随声明变更核对。

新建包文档使用 `Documentation~/README.md` 为包内导航。已有 `Document/`、`Documentation/` 或 `docs/` 原地保留；先确定正文权威性，再逐包迁移。目录名统一不是内容通过验收的依据。

## 3. 文档类型、核校状态与事实语言

类型说明用途，核校状态说明可信范围；两者分别记录。

| 类型 | 应包含 | 不应据此宣称 |
| --- | --- | --- |
| 能力地图 | 能力边界、依赖方向、选型和专题入口 | 已覆盖全部实现细节 |
| Canonical 设计 / 工程规范 | 契约所有权、设计取舍、流程、约束、证据 | 规范要求已在全仓实现 |
| 使用指南 / API 参考 | 前置条件、调用步骤、参数和结果、所有权、失败行为 | 包未验证的环境也受支持 |
| 教程 / 接入指南 | 可完成的目标、操作顺序、预期结果与排错 | 示例策略是框架默认策略 |
| 示例分析 | 示例如何选择和组合能力、哪些部分由项目接管 | 示例可直接用作所有项目的默认架构 |
| 历史审计 / 验收记录 | 日期、源码基线、命令、结果与未覆盖项 | 旧测试结果证明当前版本已通过 |
| 演进计划 / 提案 | 目标、状态、确认范围、依赖与验收条件 | 待确认或计划中的行为已经实现 |

| 核校状态 | 允许的声明 |
| --- | --- |
| 待核校 | 仅保留入口，正文尚未对照当前实现；列出具体待核点 |
| 部分核校 | 标明已核对章节、源码范围、环境与未核范围 |
| 已核校 | 本文声明的适用范围已按第 7 节完成检查；不外推到其他版本和平台 |
| 历史记录 / 已取代 | 开头注明有效日期或范围，并给出当前入口；没有继任文档时明确待补 |

旧文档没有标记时，不能默认其已核校，也不因日期久远直接判定其全部过时。改动日期不是事实核校日期；只修改导航、格式或链接时，不更新正文的事实基线和证据等级。

正文区分**规范约束、当前实现、示例策略、目标设计、已知限制、历史结论**。证据等级继续沿用[治理路线图的 E0–E5 定义](../11-DocumentationCompletionPlan.md#32-证据成熟度)，逐项注明覆盖范围；文档格式、链接检查与包发布资格分别验收。本文是规范文本，运行时证据等级不适用。

## 4. 最小结构与模板

按实际复杂度裁剪标题；不要求每页都有图或大段背景，也不创建尚无内容的空文件。复杂生命周期、恢复链和跨包交接优先用 Mermaid，简单字段用表格。示例应链接实际源码；内嵌代码注明完整示例或片段，片段须交代省略的装配条件。

### 4.1 包根 README

```markdown
# <包名>

一句话说明能力与使用场景。

## 定位与环境
负责的能力、调用方、环境要求与关键限制。
版本及直接依赖见 package.json；说明必要的可选依赖。

## 安装与首次使用
已验证的安装方式、必要配置、最短调用或真实样例链接。
给出预期结果和所有者的释放责任。

## 文档与样例
链接 Documentation~/README.md、包内样例和 CHANGELOG.md（存在时）。

## 限制与兼容
正式支持、实验或兼容入口；链接迁移指南。
```

### 4.2 包内使用指南 / API 参考

```markdown
# <能力>使用指南

> 文档类型：使用指南
> 适用范围：<包版本或可定位的源码基线、环境>
> 核校状态：<待核校 / 部分核校 / 已核校及具体范围>
> 事实基线：<真实核校日期；未核校时写待核校>

## 目标与前置条件
使用场景、必要对象、配置及不适用场景。

## 接入步骤与预期结果
从包内可达的样例或可复制代码开始；交代输入与结果。

## 使用契约
参数、单位、返回值、顺序、所有权、生命周期和失败行为。
按实际情况补线程、分配、确定性和重入限制。

## 常见问题与迁移
症状、原因与处理；旧 API、替代入口与兼容范围。

## 验证范围与关联文档
实际核对的源码和包内样例；测试结果注明日期和环境。
没有执行验证时写明原因；本地链接均留在包内。
```

### 4.3 仓库设计文档

```markdown
# <能力或跨包契约>设计

> 文档类型：Canonical 设计
> 事实基线：<真实核校日期、tag 或 commit>
> 核校状态：<状态及具体范围>

## 1. 能力定位与边界
问题、读者、负责与不负责的范围。

## 2. 模型、职责与源码入口
核心对象、依赖方向、权威数据和所有者；链接当前源码。

## 3. 执行流程与生命周期
创建、正常运行、失败、取消、恢复和释放。
复杂流程用图，说明跨包交接与扩展端口。

## 4. 设计决策与替代方案
为什么这样划分；项目策略与框架机制的界限。

## 5. 使用路径
链接包使用文档和跨包教程；只保留解释设计必要的片段。

## 6. 事实状态、验证与限制
分开规范、实现、目标和限制；证据逐项标注 E0–E5。
给出真实调用路径、验证入口和未覆盖链路。

文档类型：Canonical 设计 | 事实基线：<日期> | 证据等级：<分项范围>
*文档版本：v1.0 | 最后更新：<日期>*
```

### 4.4 跨包教程与历史材料

教程按“目标与前置条件 → 步骤 → 每步预期结果 → 验证 → 排错 → 深入阅读”组织，并注明宿主环境与配置来源。跨包 API 规则回链对应包，装配关系回链设计。

历史审计开头声明日期、核校范围和当前入口。提案标明待确认、已确认范围、实施中、已完成或已取代；确认与否以可追溯记录为准。迁移文档列出旧 → 新映射、行为差异、消费者和回退方式。

## 5. 导航、命名与引用

- 仓库根 README 介绍产品并导向门户；门户按读者任务分流；设计索引与包索引分别组织自己的主题，避免在所有入口复制完整清单。
- 同一主题在设计与使用文档中可以同时出现，但应各自回答相应问题并引用权威契约，不能保留两份相同规则。
- 沿用现有主题编号。新文件按能力或契约命名，正文标题使用清晰中文；不使用“最新”“最终版”“新设计”等无法持久区分的名称。
- 使用 UTF-8、文档相对链接与 C# 等代码语言标记。共享链接的目标必须在交付中存在；本机报告写成 `local/...` 文本路径。
- 标题被用作锚点时，改名也属于引用变更。源码行号只是定位提示，类型和方法名称仍须核对。
- 飞书等发布视图从仓库权威文档导出，不能形成独立维护的第二份正文；导出操作遵循[发布指南](../FeishuOfflineExportGuide.md)。

## 6. 维护责任与变更流程

文档随所属代码和契约维护。修改契约的贡献者同步更新其说明，评审者核对源码、调用方与文档是否一致；尚未指定个人负责人时写明维护范围，不编造 owner。

| 变更触发 | 需核对的文档 |
| --- | --- |
| 公开 API、默认行为、失败语义或所有权改变 | 包内契约、README 示例、迁移说明与 CHANGELOG |
| 跨包装配、生命周期、同步或恢复路径改变 | 对应设计专题、跨包指南和真实调用链证据 |
| 安装方式、环境或直接依赖改变 | package.json、包 README、独立消费说明 |
| 样例、命令、测试门禁或验证环境改变 | 引用该入口的教程和验收说明；结果仍按具体运行记录 |
| 文档移动、标题改名或正文合并 | 入链、锚点、包索引、设计索引、导出脚本及历史链接 |

执行顺序为：定位权威正文与消费者 → 核对当前实现 → 修改所属正文及必要导航 → 执行受影响检查 → 记录已核范围和剩余缺口。仅变更入口时，不能顺带提升历史正文的核校状态。

新增文档前先找现有专题；只在读者、契约或责任确实不同时拆页。若发现实现与规范冲突，记录差异并按领域规则处理；文档整理不授予机制变更许可。

## 7. 验收与现有检查边界

| 检查层 | 完成条件 |
| --- | --- |
| 结构与导航 | 从所属索引可达、类型和适用范围清楚、没有重复权威正文 |
| 使用文档 | 安装前置条件、可达样例、预期结果、所有权和失败路径明确；包内链接可独立解析 |
| 设计文档 | 源码、真实消费者、跨包边界与生命周期对应；目标设计未混入当前实现 |
| 事实与证据 | 核校状态有范围；命令结果有日期和环境；未运行和未覆盖项明确 |
| 迁移与交付 | 引用者同步、旧路径有处置、运行报告未入库、检查结果如实记录 |

复用已有入口，不新增同义“文档通过”门禁：

```powershell
# 仓库根目录；按本次修改选择 --package，可重复指定。
python -X utf8 tools/check_repo_structure.py --strict --staged-outputs
python -X utf8 tools/check_repo_structure.py --strict --package com.abilitykit.triggering
git diff --check
```

运行前按[产物规则](../../../.claude/skills/test-artifacts/SKILL.md)将日志写入 `local/Logs/`。现有结构检查默认覆盖仓库共享文档、包总索引和包维护指引的 UTF-8、常见 Markdown 本地路径；`--package` 另检查所选包及越界链接。不验证远程 URL、标题锚点、API 正确性、示例编译或正文事实。命令和示例发生实质变化时运行相应已有 gate；仅编辑规范或导航不要求重跑游戏行为测试。

检查失败区分新增问题与既有问题，明确路径、原因和处置；不能将未通过写成通过。只存在检查命令或 gate 配置，不代表执行过或已接入 CI。

## 8. 存量治理与退役

1. 先建立按文件或包可追溯的盘点，区分缺入口、缺契约、事实漂移、重复正文和历史材料。结构扫描不判定 API 正确性。
2. 每批选一个能力域，沿真实调用路径核对设计和使用文档。优先处理错误 API、生命周期与恢复语义、安装失败等会误导使用者的问题。
3. 原地修复权威正文；重复内容合并后，旧路径保留短说明与继任链接。没有明确消费者证据时保留并标待核。
4. 移动 Unity 可导入资产时保留原 `.meta` 与 GUID，并核对目标目录的导入规则。跨 `Document/` 与 `Documentation~/` 的迁移需检查导出和发布消费者。
5. 每批记录旧 → 新映射、实际检查和未覆盖范围。历史提案和验收结论保留原含义，不能批量刷新日期或删除旧结论来表示完成。

后续按[实施路线图](../11-DocumentationCompletionPlan.md#10-文档体系分层整理2026-11-24)推进。完成一批指该批范围已验收，不表示全仓文档或包已具备发布资格。
