===== 00-AbilityKit Orientation.log =====
------------------------------------------------------------------------
AbilityKit Orientation
------------------------------------------------------------------------
从工具集合、按需组合、纯逻辑优先三个角度理解当前项目

AbilityKit 不是一个必须整包接入的单体框架。
它更接近一组玩法逻辑工具包：项目需要什么，就组合什么。
------------------------------------------------------------------------
------------------------------------------------------------------------
它主要解决什么问题
------------------------------------------------------------------------
  1. 把技能、触发、标签、流程、状态机、World 等玩法逻辑拆成可复用模块。
  2. 让核心逻辑先在纯 C# 环境里验证，再交给 Unity、MonoGame 或服务器宿主驱动。
  3. 用配置、注册表、上下文和执行器，把数据和运行时行为解耦。
------------------------------------------------------------------------
------------------------------------------------------------------------
读 sample 的推荐姿势
------------------------------------------------------------------------
  - 先运行 Onboarding，建立整体心智模型。
  - 再看 Foundation / Tags / Config，理解基础词汇和数据入口。
  - 然后看 Pipeline / Flow / HFSM / Triggering，理解行为编排。
  - 最后看 World 和 Demo，理解模块如何落到完整运行环境。
------------------------------------------------------------------------
------------------------------------------------------------------------
一个最小玩法需求的拆分
------------------------------------------------------------------------
  需求: 玩家释放火球术
  标签: Cast.Fireball
  是否需要目标: 是，进入 Targeting / Tags
  是否需要时间过程: 是，进入 Flow / Pipeline
sample 后续会不断把这类需求拆成更小的工具组合。

===== 02-Package Composition Path.log =====
------------------------------------------------------------------------
Package Composition Path
------------------------------------------------------------------------
用一个玩法需求演示如何挑选 AbilityKit 模块，而不是整包全接

------------------------------------------------------------------------
按需组合不是少写代码，而是少背不需要的复杂度
------------------------------------------------------------------------
  1. 只需要技能释放前检查
  推荐模块: GameplayTags + Pipeline
  组合理由: 用标签描述状态，用 Pipeline 串联 PreCheck / Consume / Execute。

  2. 需要持续 Buff 和衰减
  推荐模块: Modifiers + Continuous + Flow
  组合理由: Modifier 管属性变化，Continuous/Flow 管持续时间和阶段推进。

  3. 需要副本、房间或服务器战斗
  推荐模块: Host + World.DI + Pipeline + Triggering
  组合理由: World 承载生命周期和服务，Triggering/Pipeline 承载玩法规则。

  4. 需要完整技能最佳实践参考
  推荐模块: demo.moba.* + 按需复制真实需要的模块
  组合理由: moba 示例是参考工程，不是所有项目的必选依赖。

------------------------------------------------------------------------
------------------------------------------------------------------------
新人继续阅读的路线
------------------------------------------------------------------------
  - Foundation：先看日志、事件、对象池、类型注册这些底座。
  - Tags / Config：再看数据如何描述玩法概念。
  - Pipeline / Flow：然后看一次性阶段和跨帧流程。
  - Triggering / HFSM / Modifiers：最后看规则、状态和属性如何互相驱动。
  - World / Demo：把模块放进可运行世界，理解生命周期和集成边界。

Tag Requirements Overview

=== Tag Requirements 概述 ===
------------------------------------------------------------------------
【1】GameplayTagRequirements 概念
  - Required: 必须包含的标签（All 匹配）
  - Blocked: 不能包含的标签（Any 匹配）
  - Exact: 是否精确匹配（默认 false，支持层级匹配）

【2】创建需求条件
  TagRequirements.RequiredCount: 2
  TagRequirements.BlockedCount: 1
  TagRequirements.Predicate: Require Buff.AttackSpeed + Unit.Hero, Block Status.Dead
需求: 需要 Buff.AttackSpeed + Unit.Hero，阻止 Status.Dead

【3】测试场景
场景 A - 角色拥有: Buff.AttackSpeed, Buff.MoveSpeed, Unit.Hero
  TagRequirements.SceneA: True
IsSatisfiedBy: True

场景 B - 角色拥有: Buff.MoveSpeed, Unit.Hero (缺少 AttackSpeed)
  TagRequirements.SceneB: False
IsSatisfiedBy: False

场景 C - 角色拥有: Buff.AttackSpeed, Unit.Hero, Status.Dead
  TagRequirements.SceneC: False
IsSatisfiedBy: False

【4】快捷构造方法
  GameplayTagRequirements.Require(tag1, tag2)
    -> 只有 Required，无 Blocked

  GameplayTagRequirements.Block(tag1, tag2)
    -> 只有 Blocked，无 Required
  TagRequirements.QuickRequire: 2
  TagRequirements.QuickBlock: 1
快捷 Require: 2 个必需标签
快捷 Block: 1 个阻止标签

【5】典型应用场景
  - 技能释放条件: 需要某些 Buff 才能释放
  - 伤害修正: 对特定目标生效
  - Buff 叠加规则: 互斥的 Debuff
  - 目标过滤: 选择特定类型的单位
