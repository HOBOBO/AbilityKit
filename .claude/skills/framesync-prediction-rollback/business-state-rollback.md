# 业务状态回滚契约

适用于 AbilityKit 业务回滚接入与审计，依据 2026-11-17 用户确认。MOBA 的机制准入以 [MobaMechanismGovernance](../../../Docs/MobaMechanismGovernance.md) 为准；本契约不扩大已批准的对象重建、协议兼容或跨会话恢复范围。

## 1. 可选扩展与启用边界

- **能力与启用分开。** 普通业务不以回滚为前提；ECS 和非 ECS 业务均可独立正常推进。MOBA 帧同步使用的模拟机制当前都需要提供回滚实现，但仅在会话实际启用回滚时接入相应捕获、日志记录与恢复流程。
- **按需约束，不限制所有项目写法。** 以下状态建模与恢复准入只约束声明需要回滚的业务及其依赖链，不作为普通项目的通用编码禁令。普通业务可以使用任意合法对象模型；接入回滚时先诊断不支持的字段、依赖与副作用，给出位置/原因/改造要求，再补齐支持。静态诊断是提示和定位能力，不代表任意代码均可自动证明正确；启用回滚前仍须修复必要缺口或明确拒绝该组合。
- 沿现有装配和选项控制回滚扩展，不为本规范凭空新增统一开关 API。关闭回滚时，不强制解析回滚专用 Provider / Command log，不为未启用的回滚逐帧保存快照或命令历史。若同一数据还用于 hash、同步或正常业务，按该用途单独判断，不能随回滚关闭而删除。
- 开启后必须检查当前机制的 Provider、结构恢复 handler、状态覆盖及保留窗口；缺失支持应在装配或完整预检中明确拒绝，不能静默降级为部分恢复。仅完成注册不代表状态完整。

Brain 试点已在显式 Capture/Validate/Restore 入口落实此边界：普通 `BehaviorState.Set` 和未声明恢复能力的策略可正常运行；请求恢复支持时按字段名、类型或依赖指出缺口。此处是运行时诊断，尚未新增针对任意业务的静态分析器；既有生成组件 analyzer/pin 检查各自声明的覆盖范围。
- 验收分别覆盖关闭时正常推进与开启时恢复重演；不能用关闭功能来掩盖 MOBA 所需能力未实现。

## 2. System 管推进，数据按原归属恢复

模拟由正式 Entitas WorldSystem 按固定 Phase / Order 调度，使用世界帧号和确定性时间。System 可以调用 `Service.Tick(frame, dt)`，服务内部的 `TickSchedules`、算法和数据结构可以保留。禁止独立 timer、后台线程或自取墙钟另行推进模拟；表现计时按其表现职责处理。

恢复由既有协调器编排预检、结构回退与状态导入，不要求把 Restore 本身变成玩法 Tick System。

| 对象/内容 | 权威归属与恢复方式 | 注意点 |
|---|---|---|
| ECS 组件值及组件存在性 | 生成组件序列化及声明的组件 Provider | 按 coverage 核实 provider / immutable / projection / transient；不能假定所有字段自动覆盖 |
| 非 ECS Service / Runtime 的纯数据 | 对应 `IRollbackStateProvider` 导出/导入 | 保持业务所有权；不为回滚强制迁组件 |
| 未来调度、延迟任务、阶段游标 | 随所属组件或 Provider 保存 | 包括 due frame、次数、取消状态、稳定顺序、冻结参数和所需策略描述 |
| RNG、身份分配器 | 各自唯一权威 Provider | 保存精确进度，引用者重绑；不复制另一套随机流或 allocator |
| 创建/销毁等结构变化 | 已定名单恢复协议或类型化 `CommandRollbackLog` | ECS 与非 ECS 都须有明确结构恢复负责人；避免名单与额外创建事件重复撤销 |
| 服务引用、委托、订阅、缓存索引 | 恢复数据后按稳定身份静默重绑/重建 | 不序列化对象引用、闭包或完整运行时对象图 |
| 外部输出、表现、诊断 | 既有提交/对账边界 | 恢复内存不能撤回已发送输出，不以补发玩法事件代替对账 |

组件是一种状态归属方式，不是回滚能力的前提。例如 Launcher 仍可关联 Service 内的 schedule，由正式 Projectile System 调用 Service.Tick；补齐 schedule 的 Provider 数据、稳定依赖重绑和合法性检查即可按既定契约修复。发现恢复缺口时先补齐原所有者的状态，不默认拆新 System、移除服务 API 或迁移所有权。

### 2.1 业务代码的状态建模准入

本节依据 2026-11-18 用户确认及后续“涉及到需要回滚的时候才做代码层面的提示”澄清执行。仅用于接入回滚或新增、实质修改已声明支持回滚的跨帧模拟代码；普通业务不因未满足本节而禁止正常运行。既有回滚实现逐域迁移，不能据此宣称已全部合规，也不自动扩大对象重建范围。

- **先声明充分状态，再接恢复适配。** 对影响后续帧结果的可变字段，列明权威存储、捕获者、恢复者及结构负责人。新增字段必须纳入原恢复路径，或证明其为可派生/临时数据；只在 coverage 写 Provider 名不算覆盖。
- **权威状态与运行时依赖分离。** 计时、游标、资格、冻结参数和必要顺序应能独立备份；服务、策略实现、委托、订阅、实体/组件引用归运行依赖。ECS 与非 ECS 一致；可用字段分组或独立 State 表达，不要求每个字段拆类，不因托管类型直接转专属 Provider。
- **业务变更、状态恢复、依赖重绑各守边界。** 正常 Apply/Activate 可以结算玩法；Restore 恢复充分状态；Bind 只恢复关系。不允许恢复调用正常入口后再覆盖值来抵消中断、准入、抽样或历史效果。可复用无副作用的底层赋值/校验，不靠散布 `isRestoring` 开关改变正常业务含义。
- **跨帧关联能重新定位。** 持久关系用稳定 ID/handle 或明确的同实例身份合同；局部引用和缓存允许保留，但须说明恢复、实体池复用或实例替换后的失效/重查规则。相同领域键不能自动证明是同一代实例。
- **派生、临时和权威数据必须分清。** 可从恢复状态确定性重建且不提交玩法的缓存可不存；影响资格、执行顺序、RNG、到期结果而不能等价重算的内容必须保存。帧内输出只有证明在下次读取前必被重算/清空，才能标为 transient；“每帧重置”本身不是证据。
- **明确查询的副作用。** 新增求值接口应区分内部计算/缓存失效与对外玩法通知；恢复使用已批准的无玩法副作用路径。既有带通知查询须登记，不借规范修改普通通知合同；资源静默读取的批准不自动扩展到所有属性操作。
- **恢复失败不得伪装成功。** 开启回滚后，捕获或导入失败不能吞掉异常后写空状态、忽略失败返回值或跳过必要目标。只读预检验证可证明的格式、身份和依赖；未知插件的任意 Restore 行为不能靠先执行一次来验证。仍按第 4 节处理实际 Import 故障，不承诺预检能证明任意代码不会失败。

唯一权威归属不等于只有一个方法可以写字段；合法 System/领域操作仍可更新所属状态，也不要求为每次赋值加 Command。状态拆分应服务于独立备份和明确依赖，不增加与业务状态竞争的影子状态，不预造任意对象图序列化平台。

结构恢复继续使用已批准的名单/类型化 Command 协议。需要新工厂或重建范围时，先证明能在不执行出生/进入玩法的情况下建立合法骨架，并按机制治理确认。纯状态与运行依赖分离不代表已经获得任意对象重建资格。

## 3. 完整帧状态与 Command

检查点是**第 N 帧完整结算后的充分状态**。恢复后从 N+1 重演已记录输入，经正常 System 树推进；同一帧不能再独立补一次物理、调度或历史业务回调。

- 已发生 Hit / AreaEnter / End 的效果应已落入状态，不保存它们的事件副本来重放。未来尚未执行的延迟任务是状态，必须保存；不能因为“事件不回滚”就无条件清空任务队列。
- 区分帧内待消费通知与未来任务：按现有帧末结算和 Capture 门禁处理前者，不能捕获未结算状态，也不能在 Import 静默清掉缺失的权威待办来伪装恢复成功。
- 除对象字段外，检查名单、身份分配器、稳定处理顺序、到期帧、资格集合、所有者/retain、配置版本和跨 Provider 关系。比如 swap-back 列表的顺序影响共享 RNG 消耗时，恢复必须保留等价的确定性顺序，不能任意按 ID 重排。
- 结构命令携带帧号、确定性 Order、类型、版本和数据载荷，按现有 `CommandRollbackLog` checkpoint 逆序回退。创建于 N 之后的对象应移除；N 时已存在但后来被销毁的对象，只在已支持的重建范围内恢复身份/骨架，再由字段 Provider 还原数据。
- 不使用 `Action`、闭包撤销栈、普通通知历史或“重新执行 Spawn/Enter”作为第二套恢复链。已有全量名单恢复能正确处理的生命周期，不额外添加重复创建日志。
- 同会话保留窗口内的 journal 回退不等于重连/跨进程基线；“纯数据载荷”也不保证所有运行时对象可重建。缺失 Cast / Continuous 等超出现有支持范围时按既定预检拒绝，不擅自扩展重建协议。

## 4. 静默重绑与失败边界

恢复字段后可重建索引、订阅和稳定身份关联；必须保持恢复值，不经正常 Enter/Exit、Added/Removed、伤害、触发或准入回调再次结算。不序列化运行时依赖本身；动态策略应保存明确的数据描述，重绑原权威服务。原有每次发射重新取样的 EventSample 语义与冻结参数不能互相替换。

MOBA 已确认：恢复 SkillLoadout 导致的被动重绑不重新评估已恢复 interval 的 `RequireOutOfCombat`；正常配置变化继续原规则。不要将这一恢复例外扩大到正常模拟。

全量快照及跨 Provider 预检通过后，按既有协调器顺序先结构、后字段恢复。预检拒绝应零导入。现有协调器不保证跨 Provider 全局事务：Import 中途失败可能已修改世界，必须沿现有失败门禁停止推进/输出并重建或重同步，不能继续假装原状态有效。局部原子导入使用的操作前备份/补偿仍须保留，它们不属于多余的按帧回调历史。

## 5. 实施与验收

先从会话和代码确认启用状态、实际装配入口、System 驱动链及已有批准，不因旧提案写着“待确认”就重复询问已批准决策。为目标机制列出“权威状态 → 捕获者 → 恢复者 → 结构负责人 → 静默重绑 → 不支持边界”，以此定位缺口。仅在实际新增/改变机制或恢复范围时按治理文档提交方案。

接入回滚或新增、实质修改已声明支持回滚的跨帧机制时，按第 2.1 节提供受影响的状态账本即可，不为无关字段重复审计：

| 字段/关系 | 权威/派生/临时/运行依赖 | 唯一存储与修改入口 | 捕获/恢复及存在性 | 身份/结构负责人 | 重绑/失效/失败边界 |
|---|---|---|---|---|---|
| 按实际受影响字段填写 | 派生/临时须说明重算或清空早于读取 | 不重复存同一权威值 | 组件生成或所属 Provider | 复用批准协议 | 无回调结算；不支持明确拒绝 |

先复用生成组件 codec 或所属领域的纯数据序列化；仅有证据表明重复适配成为问题时再设计通用能力。静态门禁检查形状、标注和部分禁止调用，不能替代状态充分性及无副作用的行为证据。不得以减少 Provider 数量、删除必要预检或只比较末帧 hash 作为规范收敛成果。

按改动范围验证有业务意义的行为：

1. 关闭回滚时，无回滚专用依赖也能正常创建、推进、取消和清理；开启时验证完整装配，缺失能力明确失败。
2. 在任务开始前、进行中、完成/取消后捕获；推进后恢复到 N，核对状态、名单、身份和关联，且恢复过程不产生历史玩法效果。
3. 用相同 N+1 起输入重复重演，逐帧比较相关 Provider 载荷/hash 及实际业务结果（次数、位置、到期帧、随机取样和身份）；只比较 trace 或最后一帧不够。
4. 涉及结构时覆盖 N 后创建对象的移除及支持范围内的销毁恢复，含池复用；涉及延迟工作时验证下一次到期只执行一次，取消后不复活。
5. 覆盖非法依赖、缺失身份和跨 Provider 不一致的零导入预检；触及 Import 故障时验证既有补偿或停止推进合同。通过正式装配确认帧驱动唯一且顺序正确。
6. 托管 State 验证快照独立性：捕获后原地修改对象/集合不能污染备份。恢复过程核对无历史玩法、无 RNG 取样、无新业务身份；必要骨架重建和 allocator 状态写回应按已批准合同验证，不能误当作普通业务创建。
