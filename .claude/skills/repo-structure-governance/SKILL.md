# AbilityKit 仓库结构治理

统一的是每项能力的权威入口和维护责任，不是把工具、文档、测试挪进同一棵目录。先查现有入口，能扩展就不新建；目录治理不扩大任务范围，也不替代根 `AGENTS.md` 或下级目录的约束。

## 按职责确定落点

| 对象 | 归属与权威入口 |
|---|---|
| 正式工具 | 按下文「工具准入与退役」定归属；仓库级入口从 [`tools/README.md`](../../../tools/README.md) 导航，包内工具从包内文档导航。实际参数以脚本或 CLI 为准。 |
| 正式文档 | 按[包文档分工](../../../Docs/design/10-EngineeringQuality/10-FrameworkPackageEngineeringStandards.md#6-文档的权威来源)选择位置：包入口和使用契约应能随包独立阅读，跨包设计先查 [`Docs/design/00-index.md`](../../../Docs/design/00-index.md)。更新现有权威章节，不复制正文；类型、事实状态和证据等级按 [design-docs](../design-docs/SKILL.md)，当前行为以源码和可复现证据核对。 |
| 测试源码 | 跟被验证契约走：沿用所属 `.NET` 测试工程、Unity 包测试程序集、Server 测试工程或工具自测。先补现有 suite；只有执行环境、依赖边界或维护归属确实不同时才新建工程。跨模块验收放已有对应的验收 suite，不把同一断言在几个层重复实现。 |
| 回归门禁 | 需要作为正式回归入口时，优先复用 [`tools/test-gates.json`](../../../tools/test-gates.json) 已有 gate；只有执行条件、失败责任或阻断时机不同时才新增。用 `./tools/run_test_gate.ps1 -List` 核对当前配置，用 `-Gate <name>` 执行；gate 配置存在不代表 CI 已接入或已经跑过。 |
| 产物与基线 | 盘点草稿放 `local/`；本地运行的日志、TRX、结果 XML 按 [test-artifacts](../test-artifacts/SKILL.md) 输出到 `local/Logs/`，CI 使用实际工作流显式指定的目录。只有被测试明确消费、可追溯且有更新方式的 fixture/golden baseline 才随对应 suite 入库；它们不是可丢弃的运行报告。正式生成物仍遵循其现有发布契约。 |

配置、源码或工作流能查到的 gate 数量、参数、接入状态等，不在 skill 或多个文档中维护静态副本。若入口与事实冲突，核对当前源码/配置和实际调用者，只修本次涉及的漂移。

共享文档按用途从 [`Docs/README.md`](../../../Docs/README.md) 导航；源码链接用文档相对路径，可用 `#L123` 表示原行号。仅在本地存在的证据用 `local/...` 文本路径而非共享链接，不把历史结论或本机文件写成现行证据。

共享提案与决策按 [`plans/README.md`](../../../plans/README.md) 维护；草稿留在 `local/`。统一 UTF-8，提交前确认共享文档引用的计划与证据同批可用，不用本地存在性替代交付检查。

## 工具准入与退役

| 类别 | 归属与处理 |
|---|---|
| 框架共用 | 跨包或仓库级的测试、构建、校验、发布能力优先复用现行入口。仓库入口登记在 `tools/README.md`；发布等子工具链可只给专题说明入口。 |
| 项目或包专用 | MOBA、Shooter、示例、文档导出等专用工作流不当作框架通用接口。包内工具随包；现有仓库级专用命令按领域导航，有调用方时不为重分类迁移。 |
| 内部支撑 | runner 步骤、薄包装器、自测、schema、模板随所属工具；不作为平行入口，也不能因未列在索引而删除。 |
| 临时 | 一次性探针、批量修补和迁移脚本放忽略的 `local/tools/<主题>/`，不进门禁、不强制暂存。若迁移仍需让其他检出或用户可重复执行，先按正式工具准入，并写清完成后何时退役。 |
| 退役 | 已跟踪的脚本确认无现行调用、无兼容承诺且不再维护时，从工具树移除，在相关索引简记旧路径、原因、替代方向和可恢复的 Git 修订。不复制可执行正文；消费者或归属不明先待核。 |

正式工具新增或转正前，交代四件事：实际消费者和维护归属；现有命令为何不能扩展以及唯一入口；依赖、运行目录、输入、写入范围和产物落点；最小复验命令或对应测试。工具索引只做导航，细节写在入口帮助或领域说明，不建第二份清单。写入型工具优先提供只读预检或显式写入开关；保留既有默认写入契约时，写明默认副作用和安全校验方式，不在盘点时运行。涉及外部同步或发布的入口不因登记而获得执行授权。

新增或整理 Unity 编辑器入口时，先按[编辑器工具准入规范](../../../Docs/design/13-FrameworkCore/09-EditorPlatformConvergence.md#52-编辑器工具准入规范)判定归属、可见性、读写与兼容范围。不要把反射发现当正式登记，不因整理菜单遗漏资产上下文、快捷键或 `-executeMethod` 消费者。

核对测试工具是否重复时，先比对门禁预设与手工入口的调用方、宿主、筛选范围、前置步骤和结果契约。复用同一脚本不算重复入口；门禁参数和顺序留在 JSON，不另做等价包装。按[门禁与手工入口](../../../Docs/AbilityKit测试门禁与批量回归规范.md#门禁与手工入口)区分完整、单步和手工证据。

提交前复用 `python -X utf8 tools/check_repo_structure.py --strict --staged-outputs`；它拒绝暂存的 `local/tools/` 文件，但不会根据脚本名推断 `tools/` 内哪些是临时工具，准入和退役仍需按消费者复核。

## 变更步骤

1. **找入口。** 从表中只打开本次相关的索引；用调用者、配置、测试工程或 `.asmdef` 归属确认实际使用路径。排查存量时，区分已跟踪、未忽略和被忽略的本地文件，不根据扩展名判断能否删除。
2. **定归属。** 开工前写清「对象 → 归属/维护方 → 保留或新增的唯一入口 → 验证」。有现有入口就扩展它；确需新增则说明原入口为什么不适用，并只更新受影响的索引。不涉及的项标明不适用，不要求每个变更同时改工具、文档和测试。
3. **改入口要查消费者。** 迁移前盘点构建/CI、脚本、Unity/Server、文档和外部已承诺的调用；列出旧 → 新映射和验证/回退方式。兼容入口需要保留时只做代理，注明退役条件，不保留两份实现。不能确认用途的存量先列为待核，不批量移动或清理。
4. **验收有证据。** 检查受影响的链接和路径可解析、工具可按安全的本地方式调用、测试能被 runner 发现。按变更风险跑最小相关测试或 gate；区分「仅列出门禁」「实际通过」「未运行及原因」「未覆盖链路」。新增正式 fixture 同时给出消费者与重建办法。

## 渐进治理计划

1. **先防新增散落：** 按 [test-artifacts](../test-artifacts/SKILL.md) 在运行前指定产物位置、提交前检查暂存区，不以清完历史存量为前置条件。
2. **再做单域试点：** 优先盘点根目录散落的运行报告，以及一个正式入口（建议从测试门禁开始）。输出 `路径 | 类型 | 当前消费者/证据 | 保留、合并、迁移或待核 | 验证`；先修明确的入口漂移，再按确认的范围迁移，不碰来源未明、他人工作或有消费者的基线。
3. **用现有检查复核：** 仓库根目录运行 `python -X utf8 tools/check_repo_structure.py --strict`。改随包文档时，每个目标包加一个 `--package <包名>`，检查 UTF-8、常见 Markdown 本地路径及目标是否留在包内。检查器不验证远程链接或锚点；根目录与 Unity 根目录的测试输出只提醒。改 gate 配置另跑 `./tools/validate_shooter_test_gates.ps1 -ConfigOnly`。两者均不代替实际执行测试。

归档未跟踪存量时，只移动已确认类型且未找到消费者的文件；保留原相对路径和校验摘要，使用 `local/Logs/archive/`（运行产物）、`local/tools/<主题>/`（临时脚本）或 `local/`（草稿）。已跟踪工具按上述退役规则处理。有引用、仍在写入或归属不明时保留并记录理由；不自动删除、覆盖或改写夹具。
