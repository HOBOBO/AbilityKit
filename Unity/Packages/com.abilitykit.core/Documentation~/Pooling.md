# 对象池生命周期与配置契约

`AbilityKit.Core.Pooling` 提供引用类型对象的后进先出复用、作用域登记、创建配置和诊断。源码按 `Core`、`Config`、`Diagnostics`、`Extensions` 组织。它不决定玩法实体的存活期、资源卸载、线程调度或跨场景关闭策略；这些责任由使用方持有。

## 最小接入与归还责任

```csharp
using AbilityKit.Core.Pooling;

using (var scope = new PoolScope("example"))
{
    var pool = scope.GetPool(new ObjectPoolOptions<System.Text.StringBuilder>(
        () => new System.Text.StringBuilder())
    {
        DefaultCapacity = 4,
        MaxSize = 32,
        OnRelease = builder => builder.Clear(),
    });

    using (var lease = pool.GetPooled())
    {
        lease.Value.Append("本次工作");
    }
}
```

池只保存引用，不会推断业务工作是否结束，也不自动调用元素的 `IDisposable.Dispose`。`Get` 成功后调用方负责归还，归还后不得继续使用对象。工厂必须返回新的非空对象，不得重复提供仍在使用的实例。`CollectionCheck` 按引用身份检查空闲及转换中的重复归还，不证明对象来自本池，也不是跨池所有权验证。

`PooledObject<T>` 是只读值类型。句柄及其全部副本合计只能归还一次，不保证重复 `Dispose` 幂等；禁止复制后分别释放，也不要同时手动归还并释放句柄。默认句柄释放为空操作。归还异常时按下表处理，不能假设句柄已自动完成资源补偿。

## 生命周期与失败边界

工厂、`IPoolable` 回调与选项委托均在调用线程同步执行。获取和归还先调用元素的 `IPoolable` 方法，成功后再调用对应选项委托。销毁时两个回调都会获得执行机会，即使前一个失败。

| 操作 | 提交与失败行为 |
| --- | --- |
| `Get` | 无空闲对象时调用工厂。工厂抛错或返回空值时不产生可归还对象；获取回调失败则销毁当前对象，再传播原异常；销毁也失败时聚合异常。 |
| `Release` | 先执行归还回调，成功后入栈；回调失败时不入栈、不自动销毁，转换标记会撤销，调用方继续负责对象，可以在处理失败原因后重试。 |
| 溢出归还 | 空闲容量已满或被预热预留时提交销毁，再执行销毁回调；销毁失败不会重新入栈或回滚计数。 |
| 构造预热 | 按默认容量创建空闲对象；发生失败时销毁当前初始化失败对象及此前成功预热的对象。清理成功则传播原异常，清理失败则聚合初始化和清理异常。 |
| 显式 `Prewarm(count)` | 请求额外创建最多 `count` 个空闲对象，不是将总数补到 `count`。非正数无操作；失败保留此前完成部分，销毁当前初始化失败对象并释放未完成的容量预留。 |
| `Clear(false)` | 默认只移除空闲引用，不调用销毁回调；不会自动释放对象所持外部资源。 |
| `Clear(true)`、裁剪 | 先移除本次选定的空闲对象并提交计数，再逐一销毁；全部处理后原样抛出唯一异常或聚合多个异常，已提交的移除不回滚。 |

批量清理期间回调可以操作其他对象，或使池重新出现空闲对象；清理并不建立禁止再次创建或归还的关闭状态。借出的对象不会被清空、裁剪或作用域释放强制收回。

## 容量、裁剪与统计

`MaxSize` 是最大空闲数量，必须为正；不是最大活动数量。`DefaultCapacity` 必须非负，同时用于构造预热和默认裁剪目标；实际预热不超过 `MaxSize`。并发预热先预留空闲槽位，归还会计入这些预留，防止空闲容量超限。选项只在创建时读取，之后修改选项不更新池。

| 裁剪设置 | 当前行为 |
| --- | --- |
| `default(PoolTrimPolicy)`、`KeepDefaultCapacity` | 目标为默认容量。 |
| 有限 `MaxInactiveCount` | 直接以该上限为目标，不是区间触发或滞回策略。 |
| `MaxInactiveCount == int.MaxValue` | 目标为默认容量与 `MinInactiveCount` 的较大值。 |
| `KeepNone` | 移除全部当前空闲对象。 |
| `KeepAll` | 历史值与 `KeepDefaultCapacity` 完全相同，仍会裁剪；名称不表示禁止裁剪。 |
| `NeverTrim` | 跳过常规 `Trim`，仍允许 `ForceTrim`、清空及溢出销毁。 |

裁剪只删除，不创建对象以满足目标。管理器、作用域和全局门面的无参 `TrimAll()` 使用各池自己的策略；显式传入策略时统一覆盖本次目标，仍尊重各池 `NeverTrim`。`ForceTrimAll` 忽略该标志。

`Stats` 在单池锁内取同一时点的快照。`GetTotal`、`ReleaseTotal` 是尝试次数，包含失败；重复归还检查拒绝也计入非空归还尝试。预热不计入获取/归还尝试。`CreatedTotal` 统计工厂成功返回非空对象，包含随后初始化失败的对象。溢出、清空和裁剪销毁计数表示已经提交移除，不证明回调成功；`Clear(false)` 单独计入丢弃数。活动数按创建、移除、空闲及预热计数计算，不是可验证的借出实例集合。

编辑器诊断快照逐池采样，不承诺跨池同一时点。计数使用 `int`，不提供无限期累计不溢出的承诺。

## 管理器、作用域与线程边界

`ObjectPool<T>` 对栈、计数、预热预留和引用检查加锁；用户工厂及回调在池锁外执行，多个对象的回调可以并发。用户必须自行保护对象及回调。启用引用检查时，同一对象在获取、归还及销毁转换期间再次归还会被拒绝；禁用检查后不得依赖该保护。

`PoolManager` 按元素类型与规范化 `PoolKey` 区分池，同键共享延迟创建结果，首次成功创建决定选项。构造失败会移除对应失败登记，后续可以重试。批量控制取得注册表快照后在锁外执行；注销操作先撤销登记再清理，异常不会恢复旧登记。并发创建或持有旧池的调用方不会因此被阻止，需要更强关闭边界时由所有者协调。

`PoolScope` 只包装一组池；同名独立实例不自动共享。`Dispose` 先标记已释放再清理，顺序重复调用无效，清理失败后不重试。作用域使用与释放不得并发。释放后包装入口抛 `ObjectDisposedException`，但已经取得的原始池引用仍可使用；调用方必须先停止工作并归还活动对象，再关闭作用域。

`PoolRegistry` 管理命名作用域，`Pools` 提供门面。保留的 `Global` 单例不应由使用方直接 `Dispose`；`DestroyScope("Global")` 执行清空。跨作用域批量操作同样基于快照，不承诺全局关闭屏障。

管理器的按实例归还记录指向最近一次获取时登记的池，既不追溯登记前已经借出的实例，也不是一次性归还令牌；登记不会随一次归还被消耗。重复归还仍依靠目标池校验。

管理器入口会规范化默认 `PoolKey`。不要直接对未经构造的默认键或默认 `PoolConfigRequest` 调用哈希等需要有效字段的操作；请求应通过构造方法或扩展入口生成。

## 配置解析与诊断

池专用的配置层保存创建参数，不承担应用设置文件、序列化、持久化或热更新策略。`PoolConfigBuilder` 构建时复制字典；`PoolConfigModule.Configs` 暴露内部字典的只读接口视图，不是防御性副本，不承诺深度不可变。

`PoolConfigCenter` 在自身锁内按注册顺序同步查询全部提供者，再选择优先级最大者；同优先级后注册者胜出。`Unspecified` 不算命中，`Disabled` 是有效的覆盖项。提供者异常中止查询并传播。提供者不得在查询期间修改注册链或等待需要同一把锁的其他线程；这里没有回调隔离或快照遍历承诺。

同一提供者按引用身份去重，不是引用计数注册。多个句柄操作同一登记，任一注销都会移除提供者；旧句柄还可能移除同一实例后续的新登记。`PoolConfigRegistration.IsValid` 只说明句柄绑定非空提供者，不表示登记仍存在。

作用域接受工厂和兜底参数的入口每次重新解析配置链，禁用配置可以拒绝获取已经存在的池；已存在池的容量和回调不热更新。直接接受 `ObjectPoolOptions<T>` 的入口绕过配置中心。`PoolOptions.FromConfig` 将默认容量与预热数量的较大值写入池选项默认容量，因此也影响默认裁剪目标。

快照给出胜出项，冲突报告同时列出所有命中候选及来源。诊断查询本身会重新调用提供者，不应把它当作无副作用的缓存读取。

## 稳定化保留项

`KeepAll` 名称与现有语义冲突，后续应单列兼容性方案，不能在工程整理中悄悄改成保留全部对象。值类型归还句柄和配置注册句柄的生命周期限制也保持现有契约；新增租约或注册代次机制需要具体使用方和独立评审。

本轮只提供 .NET 契约测试及中文注释检查证据。Unity 编辑器适配、IL2CPP、干净消费项目和正式发布资格仍按包级发布计划验证。
