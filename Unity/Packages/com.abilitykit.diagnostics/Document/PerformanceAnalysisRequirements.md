# AbilityKit 战斗性能分析需求与窗口原型

## 目标

Diagnostics 需要回答战斗开发人员最常见的几个问题：

- 在一段时间或一段战斗帧区间内，哪些技能触发次数最多？
- 哪些技能累计耗时最高，平均耗时和长尾耗时是否异常？
- 一次技能执行经过了哪些阶段、触发器、效果、Buff 和投射物？哪一段最慢？
- 某个异常事件、状态变化或疑似死循环发生在哪个技能、实体、帧和上下文？
- 当前结果与基线相比，是调用次数增加、单次耗时增加，还是并发对象数量增加？

工具应作为 Unity Profiler 的业务视角补充。运行时默认保持低开销，详细分析只在显式开启采集或复盘导入时使用。

## 第一批业务查询

### 技能排行

按选定时间范围、帧范围或战斗会话聚合技能执行记录，至少展示：

| 字段 | 含义 |
| --- | --- |
| SkillId / SkillName | 稳定技能标识和显示名称 |
| Count | 触发或完成次数 |
| TotalMs | 累计耗时 |
| MeanMs | 平均单次耗时 |
| MaxMs | 最大单次耗时 |
| P95 / P99 | 长尾耗时，数据不足时显示为空 |
| ErrorCount | 失败、取消或预算超限次数 |
| Dropped | 关联数据是否有丢弃 |

排序需要支持 Count、TotalMs、MeanMs、P95、MaxMs 和 ErrorCount。排行只依赖摘要数据，不要求默认保留每次完整调用。

### 时间段热点

将时间轴切成帧或固定时长窗口，显示每个窗口的：

- 技能触发量和完成量；
- 技能累计耗时及占用比例；
- 同帧事件数、触发器深度、活跃投射物/Buff 数量；
- 预算超限、异常、丢弃和进度停滞标记。

点击时间段后，排行和调用链只显示该范围，避免用户从整场战斗的噪声中寻找局部尖峰。

### 区间调用耗时、分配与 GC

分析器应支持对选定帧区间或时间区间做类似 LuaProfiler 的聚合查询，但按采集级别控制成本和粒度：

| 级别 | 区间内提供的数据 | 采集方式与约束 |
| --- | --- | --- |
| Summary | 技能/阶段调用次数、累计耗时、平均耗时、最大耗时；可用时提供 P95/P99；区间总分配量、GC 次数/耗时及堆大小变化 | 只维护有界聚合器和固定时间桶；不保留逐调用记录，不为每次调用创建字符串或对象 |
| Standard | Summary 数据，加按选定维度采样的调用样本、帧分布、分配量及热点排行 | 显式开启；样本与缓冲均有容量上限，报告采样率和 dropped/evicted |
| Verbose | 可选 span 时间线、嵌套调用关系，以及运行平台确实支持时的调用点分配数据 | 仅用于短时深查；不得作为常态开销承诺，按平台标注能力与精度 |

调用统计至少应能按技能、阶段和可扩展业务维度筛选/分组，并对选定区间计算 Count、Total、Mean、Max、P95/P99；长尾统计需说明样本数和算法。调用耗时是计时器测得的 wall/elapsed 时间或线程 CPU 时间必须明确标识，不得混为一谈；嵌套 span 的 inclusive 与 exclusive 时间也应分开定义，避免父子耗时重复相加后误读为实际总 CPU 消耗。

GC 信息作为**区间级运行时指标**呈现：记录区间内可观测到的分配字节数、GC 次数/暂停耗时，以及可用时的托管堆大小变化。指标来源、平台支持度和采样精度必须可见。增量/并发 GC 的工作可能跨帧执行，因此 GC 暂停或堆变化不能简单归因到恰好触发它的某个技能或方法；逐调用分配归因仅在运行时和平台提供可靠数据时启用，并显示其能力限制。分析器不主动触发 GC，也不把堆大小变化等同于该区间分配量。

### 结果可信度与开销

- 计时和分配采集应允许独立开关；未启用的采集维度不做额外查询或记录。
- 聚合器、样本池、span 缓冲区和时间桶都有配置上限；容量耗尽时优先丢弃分析数据，不阻塞或中断战斗，并显式报告丢弃量。
- 汇总需展示采集级别、区间边界、有效样本数、丢弃/采样信息及平台能力，便于判断统计是否完整。
- 性能开销需通过 Moba 示例在相同场景下比较 Off、Summary、Standard、Verbose；记录帧耗时变化、分配变化和事件丢弃情况，再确定推荐默认值。

### 调用链和上下文

火焰图或时间线节点应能关联下列维度：

- `Frame`、单调时钟和线程；
- `RootContextId`、`ContextId`、父上下文；
- `SkillRuntimeId`、技能配置 ID、来源和目标实体；
- 阶段、触发器、Effect、Buff、Projectile 等业务类型；
- 失败原因、取消原因和安全预算命中情况。

这些字段优先复用现有 battle diagnostics/trace 数据模型，通过离线聚合或编辑器适配器生成排行；不要求在通用 profiler 核心中加入 Moba 类型。

## 采集级别

| 级别 | 默认用途 | 允许运行时数据 |
| --- | --- | --- |
| Off | 生产或不需要分析 | `NullProfiler`，不分配、不建树 |
| Summary | 常态开发 | 技能/类别计数、累计耗时、最小摘要和丢弃计数 |
| Standard | 复现性能问题 | 有限样本、帧号、上下文引用、按上限保留事件 |
| Verbose | 深度排查 | span 时间线、详细调用链、异常附近上下文 |

切换级别应通过配置或会话控制完成，业务代码只依赖 `IProfiler`/框架适配器。任何缓冲都必须有容量上限，并报告 dropped/evicted 数量。

## 窗口方向

更新后的窗口原型见同目录的 `PerformanceAnalysisWindowPrototype.svg`，布局分为：

1. 顶部过滤栏：会话、帧范围、技能、实体、采集级别和排序方式；
2. KPI 区：总耗时、技能调用数、最慢技能、P95、预算超限和丢弃数；
3. 技能排行：支持点击一行联动时间轴和调用链；
4. 时间热点：按帧或时间桶展示调用量、累计耗时和异常标记；
5. 调用链/火焰图：查看选中技能在当前范围内的阶段和子节点；
6. 详情侧栏：显示上下文、配置、来源/目标、失败原因及关联事件；区间 GC/分配摘要单独展示，不强行归因到方法。
7. 采集级别控件：显式切换 Off/Summary/Standard/Verbose，并提示当前分配和 GC 数据是否受运行平台支持。

静态 SVG 只用于确认信息层级和视觉密度。正式窗口可以先复用现有 `DiagnosticsWindow` 和 `FlameGraphSvgBuilder` 的数据准备逻辑，再根据 Moba 接入反馈决定是否使用 UI Toolkit、内嵌 Web 视图或独立 Web viewer。

## Moba 接入边界

首批只接入关键边界，不改写业务流程：

- 技能 runtime 创建、开始、完成、取消；
- 技能 phase/pipeline 阶段切换；
- trigger plan 执行和递归/同帧派发边界；
- Effect/Buff/Projectile 的创建、执行和结束；
- 安全预算命中、执行失败和异常诊断事件。

每个边界通过可选 adapter 写入稳定 ID 和上下文。关闭分析时 adapter 应退化为空实现，不能要求业务代码增加条件分支。

## 验收标准

- 关闭采集时，战斗模块不产生分析集合、字符串或逐调用堆分配；
- Summary 级别能回答技能 Count、TotalMs、MeanMs、MaxMs、时间段热点及区间级分配/GC 指标（限运行平台可提供的数据）；
- Standard/Verbose 级别能从技能行跳到帧、上下文和调用链；
- GC 指标有区间语义、来源和平台能力说明，不暗示增量/并发 GC 能准确归因到单次调用；
- 调用点分配归因只在平台具备可靠支持时启用；
- 缓冲达到上限时不中断战斗，并显示 dropped/evicted；
- 同一会话导出结果可重复解析，窗口刷新不会反复克隆完整快照；
- 对疑似死循环至少能显示预算超限、同帧事件增长、最后进度上下文和最近事件；
- Moba 业务接入只新增 adapter/埋点边界，不依赖 Unity Editor API。

## 推进顺序

1. 使用本需求和 SVG 原型确认字段、筛选和布局；
2. 在 Diagnostics 中增加通用的时间桶/维度聚合接口，不引入 Moba 类型；
3. 在 Moba 示例接入技能、触发器和效果边界，验证真实数据质量；
4. 再实现 Unity 窗口的排行、时间轴和联动火焰图；
5. 对比各采集级别的实际开销和数据质量，再根据真实问题补充基线、P95/P99、死循环预警和批量导出。
